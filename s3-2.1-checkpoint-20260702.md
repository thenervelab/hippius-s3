## 2. The headline: drain throughput bottleneck — FIXED and proven live

**Root cause:** the allocator's AIMD controller backs off toward `min_total` whenever any node's `observed_p99`
exceeds `target_p99`. `observed_p99` is the p99 of a **whole-part SSD→CephFS copy + fsync + readback-verify**
(healthy ~330–410 ms), but `target_p99` was **50 ms** — physically unreachable — so the saturation predicate fired
**every tick** and pinned the fleet write-budget at the `min_total` **1 MB/s floor**.

**Live proof (staging, `drain_fleet_estimate_bps`, breaker=0, error_bps=0 throughout):**

| Moment | Fleet write-budget |
|---|---|
| Before (pinned at floor) | **1,000,000 B/s** (1 MB/s) |
| +3 min after rollout | 421 MB/s |
| +4 min | 481 MB/s |
| +~18 min (steady) | **1,000,000,000 B/s** (1 GB/s = `max_total` ceiling) |

**≈1000× increase.** The AIMD now ramps additively (+10 MB/s/tick) from the floor to the ceiling exactly as
designed; only a genuine multi-second Ceph slowdown will throttle it. Env-tunable via `CEPHOR_ALLOC_TARGET_P99_MS`.

## 4. The one remaining FAIL is a harness false-negative — NOT a throughput miss

`drain-convergence` still reports "1 pending row for our objects in 300s." Diagnosed to root cause:

- **112 of 112** recent objects **with an `address` reached `replicated`, 0 pending.** With the budget unpinned,
  every legitimate object drained fully.
- The pending rows the harness counted are the **two negative-path MPU test objects**: `mpu-badetag` and `mpu-abort`
  in `prodgate-func-*`. Their MPU Complete was **correctly rejected/aborted** (bad-etag → #228; abort), so
  `set_object_version_address` was never called → `object_versions.address IS NULL` → the drain logs
  *"upload context not ready (address NULL or version row absent)"* and defers the part indefinitely. **This is correct
  behavior** — an un-completed MPU must not be durably stored.
- So the throttle fix did NOT cause and cannot fix this; the harness's convergence set simply shouldn't include
  intentionally-incomplete MPUs.

**A real (pre-existing) gap this surfaced:** an incomplete/aborted MPU leaves a `cephor_replication_status` **pending
row + SSD bytes** with a NULL address until the **2-day MPU reaper**, and the reaper deletes the `parts` rows without
clearing the `cephor` rows — so they become permanent **orphans**. Three such orphans are live right now, ~7.3 days
old (`19048157…`, `a56168b1…`, `94988875…` — the same IDs flagged in `s3-2.1-review-2.md`). They inflate
`drain_ssd_backlog_bytes` and generate steady WARN log noise.
