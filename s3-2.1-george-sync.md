## 1. ⛔ The blocking design conversation — `cephor_replication_status` lifecycle & `reclaim_ssd` delete authority

This is the crux that ties **R4 (mine)**, **A21/WI-20a (yours)**, and **WI-20b bulk-GC (yours)** together. `reclaim_ssd` is the single point that deletes SSD bytes; all three items change what it may delete.

**The tension:**
- **R4 (silent live-object loss, non-overridable):** a persistent `ChunkMismatch` on a *live* object marks the part `failed` (`partdrain.rs:437` cleanup + `mark_failed`), then `reclaim_ssd` reclaims aged `failed` parts and deletes the **intact SSD source** — the last good copy, since the pool copy is corrupt. `failed` **conflates** "abandoned junk (safe to delete)" with "live object, corrupt pool copy (must NOT delete)."
- **WI-20b (bulk SSD orphan-GC):** *wants* `reclaim_ssd` to delete abandoned-orphan SSD bytes.
- **WI-20a (A21 sweep):** marks orphan `pending`/`draining` rows `failed` so `reclaim_ssd` frees them — relying on `failed` = deletable.

So R4 wants `failed`-that-is-live to be **undeletable**, while WI-20a/b want `failed`-that-is-abandoned to be **deletable**. Same state, opposite intent.

**Proposal to ratify together:**
- Add a distinct **non-reclaimable `corrupt` state** (or an alert-before-reclaim gate): a `ChunkMismatch` on a *servable* version → `corrupt`, never reclaimed, alarmed; an abandoned/unservable orphan → `failed`, reclaimable.
- The **discriminator is the servability predicate** you're already using in `janitor_part_terminally_abandoned.sql` (`address IS NULL AND size_bytes<=0 AND md5_hash=''`). One predicate, used by both the R4 mark path and the reclaim gate.
- **Decisions we need:** (a) new enum value `corrupt` vs. a reclaim-time servability check — pick one; (b) which migration owns the enum change (drain `crates/.../migrations/` vs `hippius_s3/sql/migrations/`); (c) does `reclaim_ssd` gate on `failed && servability-predicate`, or on `failed && status != corrupt`?

**Until this is settled, R4 (B3) and the reclaim half of WI-20b are both parked.** Everything else on both tracks can proceed.

## 2. A21 (WI-20a, yours) — three corrections from my dig

The todo's A21 row is outdated in ways that change the fix. Full analysis was done this session; the essentials:

- **Correction 1 — the todo says "the reaper deletes parts but NOT the cephor rows." That's stale.** Both the abort path (`multipart.py:786-788`) and the reaper (`mpu_cleanup.py:79`) *already* call `fail_version_replication`. The real leak is narrower (see below).
- **Correction 2 — the abort path's backstop is structurally invalid.** `abort_multipart_upload` deletes `parts`/`mu` in a committed txn *then* best-effort `fail_version_replication`, with a comment saying "the reaper is the backstop." But the reaper finds work via `multipart_uploads JOIN parts` — which abort just deleted. So a transient failure at the best-effort call → a **permanent orphan the reaper can never see**. (This, plus legacy orphans, is the actual live A21 leak — the 3 stuck rows.) The sweep must be keyed **directly on `cephor_replication_status`**, not via `parts`/`mu`.
- **Correction 3 — reject-Complete ≠ abort.** A rejected Complete (#228 wrong-ETag) leaves the MPU *intact* (no delete), so the reaper still catches it later. The todo conflates the two; only **abort** and **legacy** rows leak permanently.
- **Predicate:** use the servability signal (§1) + a grace/last-activity gate, **not** bare "no parts row" (racy).

**Also — the soak gate is blind to A21 (your item too, Vertical A #12):** S14/R1 assert `replicated`-on-SSD count only; A21 orphans are `pending`/`draining`. So even after WI-20a clears today's orphans, a re-introduced leak (e.g. the abort bug above) is invisible to the gate. Add a "pending/draining orphan count bounded / slope ≈ 0" assertion, fed by the WI-20a swept-counter + aged-pending gauge.

## 6. Test-env gotcha (saves you the same dig)

Running the drain crates' Rust tests locally:
- DB tests (`#[sqlx::test]`) need `DATABASE_URL` → Postgres on **:5433** (`postgres:postgres@localhost:5433/postgres`). The system Postgres on **:5432 has no `postgres` role** and fails every sqlx test with a confusing `role "postgres" does not exist`.
- Coordination/tick tests are `#[ignore]` + need `CEPHOR_TEST_REDIS_URL=redis://localhost:6382/0` and `-- --include-ignored`.
- `coordination`/`tick` are behind `--features coord`; `store` behind `--features pg`. A bare `cargo test -p hippius-drain-core` silently skips all of them.
- Full gate: `DATABASE_URL=...:5433... CEPHOR_TEST_REDIS_URL=redis://localhost:6382/0 cargo test -p hippius-drain-core --features coord -- --include-ignored`
