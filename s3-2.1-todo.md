## Why now — this cutover removes a production SPOF [*spof]
On **2026-07-18** `node6-cache` froze (OVH: hardware) and **all** of prod S3 returned 5xx across **both** ATS
edge regions, because the **entire prod write path is pinned to that one node**: `api` + `arion-uploader` +
`arion-downloader` + `backup` + `hydrator` + `janitor` are bound to `k8s-v3-node6-cache` by
`local-cache-patch.yaml` (the 40 TB `local-cache-pvc` is a node-local PV). Random host failure is
unavoidable; a **total platform outage** from one node is not. The staging drain-direct architecture is the
fix (one ingest pod per node + Ceph read-fallback → lose a node, degrade not black out). So this promotion is
**not just "new arch"** — it is **removing the node6 monolith**. Full evaluation + incident RCA:
`2026-07-18-s3-resilient-cutover-remove-monolith.md`.

## Notes (technical context to keep the list actionable)

[*arch] **Architecture.** Node-local SSD ingest → CephFS pool via the Rust hippius-drain stack (`drain-allocator`
singleton + `drain-agent` DaemonSet). The API writes each part to SSD + `object_versions.address` and **never enqueues
uploads**; the **drain is the sole producer** — once a part replicates it LPUSHes an `UploadChainRequest`, the uploader
ships it to the backend and records `chunk_backend`. State machine `cephor_replication_status`:
`pending → draining → replicated | failed | corrupt`. The janitor evicts a CephFS part only once every required backend
has a live `chunk_backend` row (or the part is terminally abandoned). Cross-node reads in the SSD→pool window use
`DualFileSystemPartsStore` pool fallback. Cutover is flagless (no producer toggle; rollback = image revert). Prod
Postgres is on dedicated NVMe; prod adds dedicated SSD ingest nodes — a full SSD 503s every PUT on that node.

[*shipped] **What shipped (do not redo).** #218 (WI-1…WI-17 hardening) · #220–#225 (worker metrics, observability,
reaper safety, staging reconcile) · #227 (drain throughput throttle — AIMD `TARGET_P99_MS` 50 ms → 2000 ms, the S1
unblocker) · #228 (A7 ETag/order reject) · #230 (A1 cold-fallback DCR) · #231/#232 (lag tune, poll 5 s → 1 s) · #233
durability + #234 coordination, both rolled into **#235** · #236 (read-path A2–A5) · #237 (A6 ACL fallback, A10 DLQ cap,

`cephor:*` — sequence the restart in a window.

redis-queues is a separate host). Just confirm the alert thresholds are set post-deploy.

zero-touch quota bump** (matches the `20480Gi` manifest):
`kubectl -n hippius-s3-prod patch pvc object-cache-pvc --type merge -p '{"spec":{"resources":{"requests":{"storage":"20480Gi"}}}}'`.
To reclaim the ~2.3 TB of stale fallback data instead, clear the *directory contents* online — no PVC churn.

# PROD LOGISTICS — provisioning the SSD-ingest tier on the existing cluster

Full analysis + formulas + references live in **`s3-prod-drain-capacity-plan.md`**. Manifests are in
**`k8s/production/`** (created here, **commented out** in `kustomization.yaml` until nodes are prepped).

### Sizing (measured from prod `object_versions` + Loki, NOT the metrics — those are inflated pre-#265)
- Real ingest: **avg 32 MB/s, peak-5min 470 MB/s, peak-1min 573 MB/s, ~2.5 TB/day (peak day 5.2 TB)**;
  objects avg 21/s, peak 150/s; **bimodal** — 91% of objects <64 KB, 92% of bytes are 1–10 MB.
- Verdict: **light on bytes, heavy on count, very bursty (~18×).** Binding constraint = **drain
  throughput**; SSD is sized for **endurance/headroom**, not capacity (resident backlog ~10–25 GB).
- **Recommendation: 3–4 ingest nodes**, each `api-local` + `drain-agent`, with **1–2 TB
  write-intensive NVMe (≥3 DWPD)**. Drainers are a DaemonSet on those nodes — no separate hosts.

### Nodes are already provisioned — dedicated `/s3-data` NVMe (no OSD repurpose) [DONE 2026-07-21, #292]
Swept all five: **`k8s-v3-node1..5` each have a dedicated 3.84 TB Gen4 datacenter NVMe mounted (ext4) at
`/s3-data`** (WD Ultrastar DC on node1/3/5, Micron 7450 PRO on node2, Intel/Solidigm D7-P5520 on node4;
~empty, all `rota=0`). Each drive does ~2.5–3.4 GB/s write vs the ~115 MB/s/node demand (~20× headroom);
endurance need ≈0.13 DWPD, well under the drives' ~1 DWPD — so these read-intensive parts are fine here.
The earlier "repurpose a Ceph OSD" plan is **moot** — the disks are already there and mounted.

- **Labels applied on the live cluster:** `kubectl label node k8s-v3-node{1..5} s3-prod-local-ingest=true`
  (node2/node3 also keep `s3-staging-local-ingest` — independent selectors; staging writes the node-root
  `local_ingest_staging` path, prod writes `/s3-data`, so no disk collision).
