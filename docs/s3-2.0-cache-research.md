# S3 2.0 — Cache Tiering Research & Design Recommendations

Research appendix for the **S3 2.0 Tiered Cache Architecture** proposal
(`https://s3.hippius.com/veggies/s3-2.0.html`). Compiled 2026-06-15.

This document consolidates two adversarially-verified research passes (each: fan-out
web search → source fetch → 3-vote claim verification → synthesis). Every load-bearing
claim below is backed by a primary source and survived a 2-of-3-to-kill verification
vote. Claims that were *refuted* during verification are listed in §6 so we don't
accidentally design against them.

**Scope of the proposed architecture this informs:**
- **Edge (ATS)** — regional read-only tier, hot objects.
- **Ingest** — per-node SSD; absorbs writes, acks the client instantly.
- **Shared (CephFS)** — cluster-wide read/write; async replication target from Ingest.
- **Backends** — Arion + backup (permanent).

Relevant existing invariants in the codebase this design must preserve:
- **Janitor replication gate** — a chunk is never evicted until replicated to every
  required backend (`HIPPIUS_UPLOAD_BACKENDS` ∪ `HIPPIUS_BACKUP_BACKENDS`). See
  [workers/run_janitor_in_loop.py](../workers/run_janitor_in_loop.py).
- **Async backend writes** — client PUT acks once data hits FS cache + DB row + Redis
  queue; the uploader drains to Arion asynchronously. S3 2.0's Ingest→Shared step is
  the *same pattern one tier earlier*.
- **Immutable, content-addressable parts** — 4 MiB chunks keyed by `object_id`,
  deterministic per `(object_id, version, part, chunk_index)`. This property turns out
  to materially simplify the read-consistency design (see §4.3).

## 1. TL;DR — what to adopt

**Replication flow (Ingest SSD → CephFS):** the proven pattern is **write-back /
ack-before-persist + demote-on-eviction** (Meta CacheLib), gated by a **write-budget
admission policy** to cap replication/SSD-wear, with the **janitor never-evict-until-
replicated invariant** kept as the hard durability floor. The single-SSD ingest tier is
a **total-loss window** for un-replicated parts — strictly weaker than the systems we
studied, whose cache tiers are themselves replicated — so the durability of that window
is an explicit **policy decision** (§4.1), not a default.

**Hot/cold decision:** the modern, concurrency-friendly winners are **S3-FIFO**
(admission + eviction) and **SIEVE** (eviction only) — FIFO-based, lock-free on hits,
beating optimized LRU on both miss ratio and throughput. Use **S3-FIFO** (its ghost
queue gives you frequency-based admission for free) or SIEVE for max simplicity. Keep
**FIFO-only, no per-hit metadata writes** on the CephFS tier.

**Read consistency for un-replicated parts:** because parts are immutable, you do **not**
need CRAQ-style version machinery — **route the read to the node that holds the part**
is correct and sufficient (§4.3).

**Biggest unvalidated assumption:** SIEVE/S3-FIFO were proven on web/CDN object traces,
not 4 MiB-chunk range-read workloads. Settle this with a **trace-replay experiment** on
our own Loki access logs, not more reading (§5).

## 2. The core design axis: where you put the ack point

Every system makes the same fundamental choice — ack early (fast, lossy window) vs ack
at end-of-replication (slow, no window):

| System | Ack point | Loss window on node death | Relevance |
|---|---|---|---|
| **Ceph cache tiering (writeback)** | At cache tier; flush to base later | Bounded — *cache pool is itself replicated* | ⚠️ **Deprecated in Reef (2023)** |
| **Alluxio `ASYNC_THROUGH`** | After worker-cache write | **Total loss if worker dies before persist** (default repl=1) | Closest analog; copy its mitigations |
| **CacheLib (hybrid DRAM+flash)** | After RAM buffer (large-object path) | Single-node; demote-on-eviction to flash | Replication-flow + admission template |
| **Chain Replication / CRAQ** | At the **tail** (end of replication) | **Zero** — any acked write is fully replicated | Strong-consistency counter-pattern |
| **Netflix Open Connect** | N/A (read-only edge) | None — edges hold no authoritative data | Doesn't transfer (we absorb writes) |

The S3 2.0 Ingest tier sits at the top of this table (ack-early). The rest of this doc
is about doing that *safely*.

## 3. Hot vs cold — admission & eviction

### 3.1 S3-FIFO (admission + eviction) — recommended

Three FIFO queues: **small (10% of cache)**, **main (90%)**, and a data-less **ghost
queue** (object IDs only, sized ≈ main). New objects enter small; on eviction,
frequency > 1 promotes to main, frequency ≤ 1 demotes to ghost. ~2 bits/object (capped
counter to 3). Objects found in the ghost queue on re-insert go straight to main.
- **~6× throughput of optimized LRU at 16 threads** (lock-free).
- Built to exploit the **one-hit-wonder** property: in short request windows **up to
  ~78%** of objects are accessed exactly once (Akamai CDN studies corroborate ~60–75%).
  The ghost queue *is* the hot/cold admission decision — it keeps one-hit-wonders out of
  the main tier.
- Sources: SOSP'23 "FIFO queues are all you need for cache eviction" (Yang et al.);
  https://s3fifo.com ; https://blog.jasony.me/system/cache/2023/08/01/s3fifo

### 3.2 SIEVE (eviction only) — simplest option

One FIFO queue, one "hand" pointer, one visited-bit per object. Hits set the bit (**no
lock, no reorder**); on a miss the hand scans, clearing bits, evicting the first
unvisited object. "Lazy promotion / quick demotion."
- **~2× throughput of optimized LRU at 16 threads** (17% at 1 thread, 125% at 16) — and
  that baseline is CacheLib's *already heavily-optimized* LRU.
- **Up to 63.2% lower miss ratio than ARC**; lowest miss ratio on >45% of 1559 traces
  (7 datasets) vs 15% for the runner-up (TwoQ).
- ⚠️ **No scan resistance**, eviction-only (no admission), documented as **weaker on
  block-storage / large-object workloads** — directly relevant to our access pattern.
- Sources: NSDI'24 SIEVE paper (Zhang/Yang et al.);
  https://junchengyang.com/publication/nsdi24-SIEVE.pdf

### 3.3 TinyLFU — frequency-aware admission filter

Given a newcomer and an eviction candidate, decides from recent access-frequency history
whether the swap is worth it, using a compact Count-Min-sketch / Bloom representation.
Pairs with any eviction layer. (S3-FIFO's ghost queue gives you an equivalent
frequency-admission signal for free, so this is only needed if you *don't* pick S3-FIFO.)
- ⚠️ The "W-TinyLFU is best across all traces" claim was **refuted** in verification
  (§6) — do not claim universal superiority for any single policy.
- Source: ACM ToS (Einziger/Friedman/Manes); https://arxiv.org/abs/1512.00727

### 3.4 Why concurrency matters here specifically

The §10 incident (api/gateway liveness death-spiral) was an **event-loop saturation**
problem. Eviction policies that lock or reorder on every cache *hit* (LRU/ARC) add
exactly the kind of per-request contention that surfaced there. The FIFO-based policies
above are lock-free on hits by design — they're the right family for a saturated loop.

## 4. Replication flow — durability & consistency

### 4.1 The ack-then-async durability window (bound it explicitly)

**This is a policy decision, not a default.** The single-SSD ingest tier is a
**total-loss window**: parts written and acked but not yet on CephFS are lost entirely if
that node dies. This is *weaker* than every system we studied — Ceph's writeback cache
pool and Alluxio's worker tier are themselves multi-node/replicated, so their documented
"window" is just a flush gap, not total loss. **Do not assume the ingest tier inherits
their durability.**

Three options, framed by the evidence:

1. **Replicate to ≥2 ingest nodes before ack** (Alluxio `replication.durable=N` model:
   "write N synchronous worker copies before returning … survive N-1 worker failures
   before being persisted"). Survives one node death with zero loss. Modest write-latency
   cost. **Recommended** unless write latency is provably critical.
2. **Accept the window** — ack on one SSD, document the loss exposure. Only defensible if
   the replication lag is tiny *and* the janitor gate holds. Requires an explicit
   replication-lag SLA + alerting (the lag duration *is* the loss exposure).
3. **Ack at end-of-replication** (Chain Replication / CRAQ tail model) — zero window, but
   you've given up the instant-ack that motivates S3 2.0 in the first place. Listed for
   completeness; not recommended for the ingest tier.

**Keep the janitor never-evict-until-replicated invariant regardless.** Alluxio
independently arrived at the identical gate: it marks un-persisted blocks
`TO_BE_PERSISTED` so they are never evicted before reaching durable storage. That
convergence is strong validation that our existing invariant is the right primitive —
extend it to the new Ingest→CephFS tier.

### 4.2 CacheLib replication-flow template (Meta, OSDI'20)

The proven mechanics for the Ingest→Shared flow:
- **Ack from the fast tier, flush async.** LOC "writes a new item into an in-memory
  buffer, after which LOC will acknowledge the write"; flush happens when the buffer fills.
- **Demote-on-eviction, not write-through.** Items live in the fast tier and are written
  down only when they become eviction victims. Write-through would double every write.
- **Admission-gate the slow tier to cap write volume / wear.** Navy ships deployable
  mechanisms: **RejectRandomAP** (reject fixed P% of writes) and **DynamicRandomAP**
  (track device bytes-written, adjust rejection to stay under a **daily write budget**).
  A learned/ML admission policy cut **bytes-written-to-flash by 44% with no hit-ratio
  loss** — but training is "cumbersome"; treat as a later optimization.
- **Keep writes sequential, region-based.** 16 MB regions (configurable to 256 MB),
  evicted whole in FIFO/LRU order; sequential writes dropped device write amplification
  **1.5× → 1.05× (~15% fewer NAND writes/sec)**.
- **No per-hit writes on the slow tier.** CacheLib's small-object flash engine is
  restricted to FIFO precisely because a hit-update would force a 4 KB page write. Lesson:
  per-hit bookkeeping belongs in the fast tier only.
- Sources: https://www.pdl.cmu.edu/PDL-FTP/CloudComputing/cache-lib-osdi20.pdf ;
  https://cachelib.org/docs/Cache_Library_Architecture_Guide/

### 4.3 Read consistency for un-replicated parts — the simplifying insight

CRAQ's entire dirty/clean/version-query apparatus exists to handle **mutable** objects —
stale-value hazards when a value is updated in place. **Our parts are immutable and
content-addressable by `object_id`.** There is no stale-value hazard for an immutable
4 MiB chunk.

> **Therefore: skip CRAQ versioning. "Route the read to the node that currently holds the
> part" is correct and sufficient.** Last-writer-wins on identical content makes the
> coherence hazard moot. We already have the part→location mapping concept in
> `chunk_backend`.

This collapses the read-consistency problem from "implement chain-replication
versioning" to "track which node holds each not-yet-replicated part and route to it."

### 4.4 Recovery — durably track in-flight replication (CRAQ Sent-list)

Chain Replication's recovery template: each node keeps a **`Sent` list** of updates
forwarded-but-not-yet-confirmed; on failure the predecessor re-forwards its `Sent` list
to the new successor, guaranteeing no in-flight write is lost.

> **Apply: the replication daemon must durably record parts forwarded-but-not-yet-
> confirmed-replicated, and re-drive them on daemon/node restart.** This is the concrete
> answer to "how do I guarantee no in-flight part is silently dropped." (Our Redis
> queue + DB `chunk_backend` rows are the natural home for this state.)

- Sources: van Renesse & Schneider, OSDI'04 Chain Replication;
  Terrace & Freedman, ATC'09 CRAQ.

### 4.5 Cautionary tale — Ceph cache tiering

Ceph's *own* cache-tiering feature does exactly what S3 2.0 proposes (ack at cache, flush
to base later) — and **Ceph deprecated it in Reef (v18.2.0, 2023)** because it "degrades
performance for most workloads" and carries consistency hazards:
- Read-only mode serves **stale reads** (no sync of base-tier updates to cache).
- Writeback flush/evict can **deadlock** on certain object shapes (omap / EC base tiers →
  "Device or resource busy", object access hangs, **requires OSD restart** — tracker
  #14511).

**Mitigation:** our design replicates via a **daemon to a plain CephFS pool** — it does
*not* use Ceph's deprecated cache-tiering feature, which sidesteps the flush-deadlock
class entirely. Stay there; don't enable RADOS cache pools.

- Sources: https://docs.ceph.com/en/latest/rados/operations/cache-tiering/ ;
  https://tracker.ceph.com/issues/14511

## 6. Refuted claims (do not design against these)

These were adversarially **refuted** (0-3 or noted over-generalization) during
verification:
- ❌ **"Ceph writeback acks at the base/durable tier."** False — ack is at the *cache*
  tier (that's the whole point of the window).
- ❌ **"W-TinyLFU is best across all traces / the only scheme to achieve that."** Refuted.
  No single policy is universally superior.
- ❌ **"The Alluxio data-loss fix modified the block evictor."** False — the fix is
  persistence-state tagging (`TO_BE_PERSISTED` in `InodeTree.java`), not evictor logic.
- ⚠️ **Mode-specific, not blanket:** Ceph's "no attempt to keep cache consistent under
  object updates" line is in the *read-only-mode* section — it's mode-specific, not a
  universal writeback statement.

## 8. Source quality

All load-bearing claims are backed by primary sources: peer-reviewed papers (CacheLib
OSDI'20, SIEVE NSDI'24, S3-FIFO SOSP'23, Chain Replication OSDI'04, CRAQ ATC'09, TinyLFU
ACM ToS), official vendor docs (Ceph, Alluxio, CacheLib, Netflix Open Connect), and the
Ceph issue tracker. Two passes: 47 sources fetched, 213 claims extracted, 50 verified via
3-vote adversarial verification, 47 confirmed / 3 killed.

**Time-sensitivity:** Ceph cache tiering is *deprecated* (cautionary, not recommended).
SIEVE/S3-FIFO are 2023–2024 and still SOTA but young — limited long-term production track
record outside the authors' evaluations. Several figures are workload-scoped (the 44%
flash-write reduction is SocialGraph-specific; 6×/2× throughput are specific traces; the
78% one-hit-wonder figure is the shortest-sequence/1%-of-objects slice) and should not be
generalized.
