# S3 2.0 — Disk Replicator Daemon: Design & Rust Plan

Companion to [s3-2.0-cache-research.md](s3-2.0-cache-research.md) (the verified research
appendix) and the architecture proposal
(`https://s3.hippius.com/veggies/s3/s3-2.0-tiered-caching.html`). Drafted 2026-06-16.

> **veggies' framing:** *"the crux of the dev effort is writing a disk replicator daemon,
> and that would lend itself nicely to be rustified."*

This doc takes that at face value and plans the daemon concretely: its job, the exact
interop contract it must honor against the **existing** Python cache code, its state
machine and failure/recovery behavior, and an honest assessment of building it in Rust.

The research doc already settled the *policy* questions (ack point, durability window,
eviction family, consistency model). This doc is the *mechanism*: the actual process we
ship.

---

## 1. What the daemon is (and is not)

**Role:** a small, per-node background process that moves completed parts from the node's
local **Ingest SSD** up to the shared **CephFS** tier, marks them replicated, rings the
existing chunk-ready bell, and owns the Ingest SSD's lifecycle (absorb → replicate →
evict-under-pressure).

It is the concrete realization of the research doc's §4.2 (CacheLib write-back flow),
§4.4 (CRAQ Sent-list recovery), and the §4.1 durability gate.

**In scope:**
- Discover parts on the Ingest SSD that are complete but not yet replicated.
- Copy them to CephFS atomically, meta-last, byte-identical.
- Record the durable "replicated" marker (the never-evict gate's new lower tier).
- `PUBLISH` chunk-ready notifications so readers blocked on CephFS unblock.
- Re-drive un-confirmed parts on restart (Sent-list analog).
- Evict replicated parts from the Ingest SSD under disk pressure.
- Emit metrics: replication lag, queue depth, bytes moved, parts pending.

**Explicitly NOT in scope (stays where it is):**
- **Crypto/KMS** — chunks on disk are already AES-256-GCM ciphertext. The daemon moves
  opaque bytes and never sees a DEK, KEK, or KMS cert. This is what makes it safe to
  write in a second language.
- **Arion / chain upload** — still the Python `arion-uploader` worker. The daemon's tier
  is Ingest→CephFS only; CephFS→Arion is unchanged.
- **CephFS-tier GC + the Arion replication gate** — still the Python `janitor`. The
  daemon owns only the *Ingest* tier's eviction. Clean split (see §6).
- **Read routing** — deciding *which* node serves a not-yet-replicated read lives in the
  reader/gateway, not here. The daemon only exposes the hooks (§7).

## 2. The interop contract (the crux of "rustifiable")

The daemon talks to the rest of the stack through three stable, language-agnostic
interfaces. None of them require linking against Python. This is precisely why a separate
Rust process is viable — the contract is filesystem + Redis, not in-process calls.

### 2.1 On-disk layout (read + write)

Source of truth: [hippius_s3/cache/fs_store.py](../hippius_s3/cache/fs_store.py).

```
<root>/<object_id_uuid>/v<version>/part_<n>/
    chunk_0.bin            # AES-256-GCM ciphertext, opaque to the daemon
    chunk_1.bin
    ...
    meta.json             # {"chunk_size": int, "num_chunks": int, "size_bytes": int}
    *.tmp.<uuid4>         # in-flight atomic write; ignore (janitor/daemon GC if >1h)
```

- **`meta.json` presence = "part is complete."** This is the daemon's trigger condition,
  identical to the rule readers already use (`get_chunk` returns `None` without it,
  [fs_store.py:168](../hippius_s3/cache/fs_store.py)). The daemon replicates a part *only*
  when `meta.json` exists AND all `num_chunks` chunk files are present.
- **Atomic write discipline (must match byte-for-byte):** write to `<name>.tmp.<uuid4>`,
  `fsync` the file, `rename` onto the final path, `fsync` the parent dir
  ([fs_store.py:86-92, 335-346, 499-510](../hippius_s3/cache/fs_store.py)). The Rust
  daemon reuses this exact pattern on the CephFS destination so concurrent writers (the
  daemon on node A, a downloader filling the same part on node B) never corrupt each
  other. Content is deterministic per `(object_id, version, part, chunk_index)`, so
  last-rename-wins is harmless.
- **Ordering on the destination is load-bearing:** copy all `chunk_*.bin` first, fsync,
  then write `meta.json` **last**. A CephFS reader must never see a part dir with meta but
  missing chunks. (Same invariant the uploader honors writing meta last.)

### 2.2 Redis pub/sub bell (write-only)

Source of truth: [hippius_s3/cache/notifier.py](../hippius_s3/cache/notifier.py).

- After the CephFS `meta.json` lands, the daemon publishes one notification **per chunk**
  so any streamer blocked in `wait_for_chunk` re-checks CephFS and unblocks:
  - Channel: `notify:{chunk_key}`
  - `chunk_key` = `obj:{object_id}:v:{version}:part:{part_number}:chunk:{chunk_index}`
    ([notifier.py:29-35](../hippius_s3/cache/notifier.py))
  - Payload: `"1"`
  - Instance: the **queues** Redis (`REDIS_QUEUES_URL`, :6382).
- This is a single `PUBLISH` per chunk — trivial in any language. No subscribe side.

### 2.3 Work intake (Redis list, mirrors the uploader)

The existing async pattern is a Redis list the worker drains (e.g.
`arion_upload_requests`). The daemon mirrors it:
- **Primary:** the writer `LPUSH`es a tiny job `{object_id, version, part_number}` onto
  `ingest_replication_requests` right after it writes the part's `meta.json`. The daemon
  `BRPOP`s. (One extra `LPUSH` on the existing PUT path — cheap, same shape as the
  current upload enqueue at `put_object_endpoint.py`.)
- **Safety net / recovery:** a periodic full scan of the Ingest root for parts that have
  `meta.json` but no `replicated` marker (§4). The queue is the fast path; the scan
  guarantees nothing is ever permanently missed if a job is dropped or the daemon was
  down when it was enqueued. The doc's "on restart, rescan the ingest dir" *is* this scan.

## 3. The "replicated" marker — the new lower gate

We need a durable, per-part flag meaning **"this part is byte-complete on CephFS."** Two
candidate homes; we use the first as the authoritative gate and the second only for
observability:

1. **Authoritative: a sentinel file on the Ingest SSD.** After the CephFS copy is durable,
   the daemon writes `replicated.json` (atomic, fsync'd) into the *Ingest* part dir:
   `{"tier": "cephfs", "replicated_at": <unix>, "bytes": <n>}`. This mirrors the
   `meta.json` convention exactly — it's scannable, self-describing, survives restart, and
   needs no DB round-trip. **The Ingest-tier eviction gate is: never delete a part from the
   Ingest SSD unless `replicated.json` exists.** This is the research doc's §4.1
   never-evict-until-replicated invariant, applied one tier down.
2. **Observability only (optional): a `chunk_backend` row** with `backend='cephfs'`. Lets
   the janitor / dashboards see CephFS placement in SQL and keeps the part→location idea
   in one place (research §4.3). It is *not* the daemon's hard gate (we don't want the
   ingest eviction path blocking on Postgres). Write it best-effort after the marker.

**Crash-safety ordering (the whole correctness argument):**

```
1. copy chunk_*.bin  -> CephFS (tmp+rename+fsync each)
2. fsync CephFS part dir
3. write CephFS meta.json (tmp+fsync+rename+fsync dir)   <- part now visible to readers
4. PUBLISH notify:{chunk_key} for each chunk             <- unblock waiters
5. write Ingest replicated.json (tmp+fsync+rename)       <- eviction now permitted
6. (best-effort) upsert chunk_backend cephfs row + metrics
```

A crash before step 3 leaves an invisible partial part on CephFS (readers ignore it,
deterministic re-copy overwrites it). A crash before step 5 leaves the part replicated but
un-marked → the scan re-drives it, the re-copy is idempotent, and the marker is written.
**There is no ordering at which a part can be evicted from Ingest before it is durably on
CephFS.** That is the Sent-list guarantee (research §4.4) expressed as on-disk state.

## 4. Daemon internals

```
            ┌──────────────────────── replicator (per node) ─────────────────────────┐
  LPUSH     │  intake:   BRPOP ingest_replication_requests  ─┐                        │
 (writer) ──┼─────────────────────────────────────────────► │  bounded work queue    │
            │  scan:     every N s, walk Ingest root,        ─┘  (dedup by part key)   │
            │            enqueue meta-but-no-marker parts                              │
            │                              │                                          │
            │                              ▼                                          │
            │     worker pool (semaphore = REPLICATOR_CONCURRENCY)                     │
            │       per part:  verify complete -> copy chunks -> cephfs meta           │
            │                  -> publish bells -> write marker -> metrics             │
            │                              │                                          │
            │  pressure loop: if Ingest disk > high-watermark,                        │
            │                 evict oldest parts that HAVE replicated.json             │
            └────────────────────────────────────────────────────────────────────────┘
```

- **Discovery = queue (fast) + scan (complete).** The scan is also the restart-recovery
  path; it makes the queue a pure latency optimization, not a correctness dependency. Dedup
  intake and scan by `(object_id, version, part)` so a part enqueued twice copies once.
- **Idempotent by construction.** Deterministic content + atomic rename means re-running a
  part is always safe. No locking needed for correctness; an in-process per-part dedup set
  just avoids wasted copies.
- **Bounded concurrency** via a semaphore (`REPLICATOR_CONCURRENCY`, analog of
  `DOWNLOADER_SEMAPHORE`). Copies are IO-bound (read local NVMe, write CephFS over the
  network); a handful in flight saturates the uplink without thrashing.
- **Ingest eviction** is folded in here because the daemon is the one component that knows
  exactly when an Ingest part is safe to drop. Under pressure it deletes oldest parts that
  carry `replicated.json`; never touches an unreplicated part. (Mirrors the janitor's
  three pressure modes but for the small fast tier — see §6.)
- **Backpressure on CephFS slowness:** if the work queue grows past a threshold (CephFS is
  slow / down), the daemon keeps acking-locally writes piling up on Ingest until the disk
  hits the `fs_cache_pressure` watermark, at which point the *existing* API middleware
  already 503s new PUTs. So CephSlow degrades to "writes throttle, nothing lost." Surface
  it as a metric + alert (research §5 decision #2: the lag SLA).

## 5. Why Rust fits here (and where it doesn't)

This is the right *first* Rust component in the stack, for concrete reasons — not novelty.

**Fits because:**
- **No business logic, no crypto, no schema coupling.** It's a tight IO loop:
  scan → copy bytes → fsync → `PUBLISH`. The hard parts of this codebase (auth, ACL,
  envelope crypto, S4 append CAS) stay in Python. The daemon only needs the on-disk format
  (3-int JSON) and two Redis verbs (`BRPOP`, `PUBLISH`).
- **Throughput-critical background mover = exactly Rust's lane.** No GC pauses, no GIL,
  small fixed memory footprint, can saturate NVMe→CephFS IO with one cheap process. We
  learned the hard way ([api-gateway-liveness-death-spiral]) that piling more load onto
  Python asyncio event loops starves them; a separate native process with its own runtime
  sidesteps that entirely and won't compete for the API's event loop.
- **Ideal blast radius for a first Rust service.** If the daemon crashes or lags, the
  never-evict gate means **zero data loss** — Ingest just fills and writes throttle via the
  existing 503 path; reads of replicated objects are unaffected. It can fail safe, which is
  the property you want when introducing a new toolchain to a team.
- **Greenfield, no rewrite.** We are *adding* a process, not porting one. The Python cache
  code is untouched; the daemon is a peer that honors the same files.

**Cost / risks (be honest):**
- New toolchain in CI: a `cargo build` stage, a container image (static-link via musl or
  match the base image glibc), and team Rust fluency for on-call. One more deployable.
- The on-disk contract becomes a **cross-language API** — if Python changes the layout or
  meta schema, the Rust daemon must change in lockstep. Mitigate by treating §2 as a
  versioned contract and adding a contract test (Python writes a part, Rust replicates it,
  Python reads it back through the streamer) in e2e.
- Two implementations of the atomic-write discipline (fs_store.py + the Rust equivalent)
  must stay behaviorally identical. Pin it with the contract test above.

**Verdict:** recommend Rust. The cost is real but front-loaded (toolchain + CI), and the
component is the textbook case for it: hot, simple, isolated, fail-safe, crypto-free.
If the team wants to de-risk further, a Python v0 of the daemon (reusing `fs_store`
directly) is a 1–2 day spike to validate the *design* before paying the Rust toolchain
cost — then port the validated logic. (See §8 phase plan.)

### 5.1 Rust shape (if we build it)

- Runtime: **`tokio`** (async IO, semaphore, `spawn_blocking` for fsync-heavy copies).
- Redis: **`redis`** crate (`BRPOP` intake, `PUBLISH` bells) — or `fred` for pipelining.
- Filesystem: **`std::fs`** + `walkdir` for the scan; `notify` (inotify) is *optional* and
  probably not worth it — recursive inotify over millions of part dirs hits
  `fs.inotify.max_user_watches` and the queue+scan design already covers latency. Start
  scan-based.
- Serde: **`serde` / `serde_json`** for `meta.json` + `replicated.json` (3 ints / small
  struct).
- Config: env-var driven to match the existing convention (`REDIS_QUEUES_URL`,
  `HIPPIUS_OBJECT_CACHE_DIR` → reused as the Ingest root, plus new
  `HIPPIUS_INGEST_CACHE_DIR`, `HIPPIUS_SHARED_CACHE_DIR`, `REPLICATOR_CONCURRENCY`,
  `REPLICATOR_SCAN_INTERVAL_SECONDS`, `INGEST_HIGH_WATERMARK_PCT`).
- Observability: **`tracing`** + JSON subscriber so lines land in Loki like the rest;
  Prometheus metrics via `metrics` + exporter on `/metrics` to match the dashboards.
  New series: `replicator_lag_seconds`, `replicator_queue_depth`,
  `replicator_parts_replicated_total`, `replicator_bytes_moved_total`,
  `ingest_disk_used_bytes`, `ingest_unreplicated_parts`.
- Deploy: a `DaemonSet` (one per node holding an Ingest SSD), mounting both the Ingest PV
  and the CephFS RWX PV. This is the multi-node replacement for the single-node
  `nodeSelector` pin that caused [node6-cache-spof-outage].

## 6. Ownership split with the janitor

Keep the existing janitor in Python; give the daemon only the Ingest tier. No overlap.

| Concern | Owner | Gate |
|---|---|---|
| Ingest SSD: absorb writes, replicate to CephFS, evict | **replicator daemon** (new) | never evict Ingest part without `replicated.json` |
| CephFS tier: hot-retention GC, age buckets, pressure modes | **janitor** (Python, unchanged) | never evict without replication to `HIPPIUS_UPLOAD_BACKENDS ∪ HIPPIUS_BACKUP_BACKENDS` |
| CephFS → Arion + chain publish | **arion-uploader** (Python, unchanged) | — |

The janitor's [never-evict invariant](../workers/run_janitor_in_loop.py) is untouched; the
daemon adds a symmetric invariant one tier down. Two gates, same principle, different tiers.

## 7. Adjacent open question this design exposes (not solved here)

**Read-after-write for a part that's only on the Ingest SSD.** A GET issued in the
seconds-wide replication window finds the part on exactly one node's Ingest SSD, not yet on
CephFS and not yet on Arion (Arion upload is also async). Two viable resolutions, per
research §4.3 ("route to the node that holds the part"):

- **(a) Wait on the bell.** Reader streaming from CephFS blocks in `wait_for_chunk`; the
  daemon's `PUBLISH` (step 4) unblocks it once replication lands. Simplest; adds up to
  `replicator_lag_seconds` of latency to reads of just-written objects. Zero new routing.
- **(b) Route to the holder.** Writer registers `ingest_holder:{oid}:v:{v}:part:{pn} =
  node` (Redis, TTL); the reader/gateway routes the read to that node's API pod, which
  serves from local Ingest; the daemon clears the key when it writes `replicated.json`.
  No added latency; needs node-aware routing in the gateway.

The daemon design supports **both** — (a) needs nothing extra; (b) needs the writer to set
and the daemon to clear one Redis key. **Recommend shipping (a) first** (correct, trivial,
the lag is seconds) and adding (b) only if read-after-write latency on fresh objects proves
to matter. This routing decision is the gateway/reader's, not the daemon's.

## 8. Phased build plan

Aligns with the proposal's Phase 1/2 and the research doc's open decisions.

- **Phase A — contract + Python v0 (de-risk the design, ~days).** Lock §2 as a versioned
  contract. Write a Python `replicator` reusing `fs_store` to prove the state machine,
  the marker, the ordering, and the bell end-to-end with the existing test harness. Add the
  e2e contract test (write→replicate→read-back). This validates *mechanism* before paying
  any toolchain cost.
- **Phase B — Rust port (the "rustification").** Port the validated v0 to Rust per §5.1.
  Same contract, same tests (the e2e contract test is language-agnostic — point it at the
  Rust binary). Add CI cargo build + image. Bench NVMe→CephFS throughput (research §5,
  experiment #3 inputs).
- **Phase C — Ingest eviction + pressure + SLA.** Fold in the pressure loop and the
  `replicator_lag_seconds` SLA + alert (research §5, decisions #1/#2). Decide ≥2-node
  pre-ack vs single-SSD window *here*, informed by measured lag.
- **Phase D — DaemonSet rollout, unpin the data plane.** Deploy per-node, move the working
  set onto the daemon-managed tiers, and remove the `k8s-v3-node6-cache` `nodeSelector`
  pin. **This is where the SPOF dies** — the original goal ([node6-cache-spof-outage]).

## 9. One-paragraph answer to veggies

Yes — the replicator is the crux, and it *is* a clean Rust target: it's a crypto-free,
schema-light, IO-bound mover whose entire contract with the rest of the stack is "honor the
on-disk part layout + meta.json completion marker, and `PUBLISH` the existing chunk bell."
That contract is filesystem + two Redis verbs, so a native process slots in beside the
Python cache code with no in-process coupling and no rewrite. The correctness argument is a
fixed write-ordering (chunks → CephFS meta → bell → Ingest `replicated.json`) that makes
re-runs idempotent and makes it impossible to evict an Ingest part before it's durable on
CephFS — the never-evict gate, one tier down. The only genuinely hard adjacent problem,
read-after-write inside the replication window, is the reader/gateway's to solve and ships
fine as "wait on the bell" first. Recommend: prove the state machine in a Python v0, then
port that exact logic to Rust and unpin the data plane.
