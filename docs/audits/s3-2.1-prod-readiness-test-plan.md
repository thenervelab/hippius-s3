## 1. EXECUTIVE SUMMARY & GO/NO-GO PHILOSOPHY

The drain stack replaces the synchronous write path with an async SSD→CephFS→backend pipeline coordinated by a
leader-elected Rust allocator. This changes the durability contract from "acked = on Ceph" to "acked = on ingest SSD,
drain will replicate." **The entire risk of this cutover is that an acked object's bytes are lost or corrupted between
the client 200 and durable backend storage, or that the coordinator misbehaves under fault/load and either
double-allocates (Ceph overrun) or stalls (backlog explosion → 503 storm).**

The drain path is, by construction, crash-**safe**: SSD copy is retained on every failure, chunks are verified before
commit, and commits are `claim_seq`-fenced. Its residual losses are the **designed at-least-once seams** plus a small
set of acknowledged leaks (§Appendix A). So the job of this plan is not "prove a clean run doesn't lose data" — it is
**(a) prove the #218 fixes hold under specific faults, and (b) prove the allocator stays single-writer under Redis
pathology and failover timing.**

### What "confident to ship" means (all four must hold)

1. **Correctness invariants provably held under load AND fault.** The 8 catastrophic invariants (§5) never break
   during any load ladder, chaos injection, or allocator-pressure run — proven by a continuous-assertion harness that
   fails the run the instant any invariant is violated, not by post-hoc inspection.
2. **Performance within ratified SLOs (§4).** Per-node drain throughput, replication lag p99, backlog ceiling, 503
   rate, and recovery time all inside their ratified numbers, at the certified concurrency knee.
3. **Recovery is bounded and demonstrated.** Every fault in the chaos matrix (§8) recovers within its hard time bound
   with zero data loss and zero split-brain.
4. **No known-risk item (§11) is unmitigated or ungated.** Each ships with a fix, a monitored guard, or an explicit
   operator-accepted deferral with a blast-radius bound.

### Go/No-Go rule

**NO-GO if any single hard gate in §12 fails.** There is no "mostly green." A durability or split-brain violation is
an automatic, non-overridable NO-GO. Performance-SLO misses are NO-GO unless the SLO is formally re-ratified by the
owner with rationale recorded.

  tests/integration`, targeted e2e, static callsite audit, `trybuild`. Gate: all green.
- **`inv-guard`** — background asserter run during every T3/T4/T5 dynamic run. Scrapes Prometheus + Loki + Postgres +
  Redis; raises `GuardViolation` → **aborts the run and marks it NO-GO**.

**Harness design (from runtime-verification research):**
- **Split hard binary invariants from metric SLOs.** The catastrophic binary invariants (two leaders, unreplicated-chunk
  deletion, byte mismatch, terminal-state regression) must be **event-driven / log-and-DB tailed**, not polled — a fast
  violation between two 1–10 s scrapes is invisible to polling. Abort on the **first** occurrence, **no debounce**.
- Metric SLOs (lag, backlog, queue depth) may be **polled** with a lookbehind window **≥ 4× the scrape interval** to
  avoid false negatives, and **hysteresis** (separate trip/clear thresholds) to avoid flapping.
- **Also run offline** Elle/Knossos over the recorded operation history post-run for deep ordering anomalies (single-leader,
  no-data-loss) that a per-scrape asserter cannot see. Keep histories bounded (linearizability checking is NP-complete).
- Blast-radius model: ChAP-style — `inv-guard` is the automated circuit breaker; a breach aborts the experiment.

|---|---|---|---|---|

## 10. R3 — THE `write_allocations` LEASE-REVALIDATION RACE (verified; reclassify to PROD GATE)

**Status: confirmed real, currently untested, and the WI-18 "skip — low value" classification is wrong.**

**The bug (verified in-tree):** `run_tick` (`tick.rs:77-83`) captures `epoch` at `acquire_or_renew_leadership`, then does
`load_fleet` → `ceiling()` (the slow step) → `allocate` → `write_allocations(epoch)` with **no re-read of `cephor:leader`**.
`WRITE_ALLOC_SCRIPT` (`coordination.rs:83-99`) fences a write only against **already-written** `cephor:alloc:<id>` epochs
(`if v.epoch > epoch then return 0`). So when a new leader B (epoch N+1 via `LEASE_SCRIPT` `INCR cephor:epoch`) has taken
the lease but not yet written any alloc key, a deposed A (epoch N) finishing a slow `ceiling()` writes an epoch-N budget
that the fence lets through (nothing higher is stored yet). It survives until B's next tick overwrites it — long enough
for an agent (2 s re-pull) to enforce it, briefly exceeding B's ceiling. **Every existing fence test seeds the higher
epoch before the stale write, so this window is never exercised** (`tick.rs:168`, `coordination.rs:547,580`).

**Why "re-read the lease before the write" is NOT sufficient (external, formal):** the check→write is not atomic — a
STW/GC/scheduler pause can land after the re-check and before the write (irreducible TOCTOU). And a plain fencing token
does not help when the *lower* token reaches the resource *first* — the resource has no watermark yet, so it accepts the
stale write (FizzBee formal result; corroborated by Jepsen's finding that etcd lease locks double-hold even in healthy
clusters).

**The correct fix (in order of robustness):**
1. **Register the epoch at the resource at election time, before any slow work.** The instant the allocator wins epoch
   N+1, atomically bump a resource-stored epoch/watermark to N+1 *before* `ceiling()`/`allocate`. Now A's epoch-N write
   hits a resource that already knows N+1 and is rejected — closing the "before B wrote anything" window. (Chubby
   sequencer / etcd `mod_revision` / Kafka producer-epoch pattern.)
2. **Fold the epoch into the CAS conditioned on current leadership, not last value** — `write_allocations` succeeds only
   if `stored_epoch == writer_epoch` (or `<=`), in the same Lua/txn as the write. This is the concrete shape for our
   Redis Lua fence: have the fence read `cephor:epoch` / `cephor:leader` and reject any writer epoch below it, not just
   compare already-written alloc keys.
3. Lease TTL >> max work duration and monotonic-clock deadlines reduce the window but never close it alone.

**How to test it deterministically (the acceptance test for the fix):**
- **Rust `fail`/`failpoint`** (or `SIGSTOP`) at the `ceiling()`→`write_allocations` boundary of the deposed allocator;
  elect a successor; release. Assert the successor's resource **rejected** A's write (assert the rejection, not merely
  "no corruption"). This is T2-1's new R3 case and T4-C Tier-2.
- Optionally deterministic simulation (turmoil/madsim, seed-replayable) for the interleaving.

**Reclassification:** move from `s3-2.1-todo.md` WI-18 "skip (low value): marginal now redis is noeviction" → **prod
gate R3 (§11)**. The gap is a failover-timing race independent of eviction; `noeviction` does not address it.
