## TL;DR (the easy version)

The plan is well-shaped and correctly sequenced. Merging it with the audit changes three things:

1. **Two findings were missing from the plan entirely** and are now folded in:
   - **Data-completeness on the delete path** — the drain deletes the only good (SSD) copy without checking the part is whole against `meta.json`, and verifies only the first/last chunk. Belongs in **Phase 1** (correctness), it wasn't there.
   - **Coordination runs on a Redis that can evict its own fence** (`allkeys-lru`) — deadlocks the allocator under memory pressure. Needs an interim fix in **Phase 3** and a permanent topology decision in **Phase 7**. It was in neither.

2. **A few items move earlier.** CI runs *zero* coordination tests today — fix that *before* Phase 4 chaos, not after. And *liveness* probes + non-zero exit-on-fault move into Phase 2, because with the hard cutover a hung pod is a live outage now, not a prod-only risk.

3. **The gates get sharper.** Phase 4's "no data loss" becomes a *verified* gate (fault-inject a dropped chunk + end-to-end checksums), its chaos matrix explicitly includes Redis *eviction* and *hang* (not just a blip), and Phase 6's durability gate explicitly covers the backup-backend enqueue path.

**One framing note that colors everything:** this is a **hard cutover, no flag** — on staging *right now* the API doesn't enqueue at PUT; the Rust drain is the **sole upload producer with no fallback**. So the Phase 1/2 P1s aren't just prod-gates — they're staging-stability fixes that matter today. The current staging soak is running on un-probed, un-metriced, coordination-untested infra.

**The reassuring half:** the core engineering is solid. The delete-before-durable path is closed on the normal/common-failure paths, several past bugs are genuinely fixed (zombie double-commit, benign-deferral breaker), and the allocator/token-bucket math and producer→consumer wire contract are proptested/byte-verified. None of the P1s are rewrites — they're a completeness check, a Redis policy, a CI service, two probes, and an exit code.

## Critical context: the hard cutover (verified)

`HIPPIUS_DRAIN_GATED_UPLOAD_ENABLED` exists only in old audit docs — not in any `.py`/`.rs`/`.yaml`. `put_object_endpoint.py:198-211` + `multipart.py:1072-1081` unconditionally stop PUT-time enqueue and only persist the object address; the drain produces the upload after replication. The drain is a hard dependency of the staging write path *now*. There are **no prod drain manifests yet** — at prod cutover the drain must ship *before/with* the api image that stops PUT-enqueue, or prod uploads stall.

## Phase 1 — Land in-flight correctness (staging)

**Goal:** close the correctness gaps before anything else builds on top.

**Work:**
- Merge the append drain-direct fix (#217) and soak the merged janitor abandoned-reclaim (#214). *(plan)*
- **[P1] R1 — decay-on-`Err` in the allocation pull.** `runtime.rs:280` — the `Err` arm holds the last budget forever on a sustained Redis outage instead of decaying toward floor; the agent keeps draining full-rate into a possibly-degraded Ceph. *(plan; audit finding 6; DOC)*
- **[P1] ➕ Data-completeness check before commit/unlink.** `partdrain.rs:338-388` — the drain trusts the directory listing and never parses `meta.json`'s `num_chunks`/`size_bytes`. A part with meta present but a missing/zero-length interior chunk is committed `Replicated` and the SSD source (the only complete copy) deleted → silent truncation. Mitigated by the api writing meta *last* (happy path safe), but the delete is irreversible and the check is cheap. *(audit finding 1; NEW — not in the plan)*
- **[P1] ➕ Interior-chunk verification policy.** `partdrain.rs:330-362` — only first/last chunks are byte-verified; the "content-addressed → interior chunks trust the copy" rationale is factually wrong (chunks are path-addressed; no re-drive after `Replicated`). Either restore full readback or re-justify sampling honestly against RADOS checksums and document the residual window. *(audit finding 2; NEW)*
- **[P2] ➕ Guard + retry `mark_failed`.** `store.rs:581-597` (no `claim_seq`/status guard) + `partdrain.rs:349-360` — a spurious readback mismatch drives a healthy part to `failed` and removes the pool copy with no retry; `ssd_reclaim` then deletes the SSD source after grace = both tiers gone. Add a `claim_seq + status='draining'` guard and a bounded copy-retry. *(audit finding 10; NEW)*

**Gate:** drain-direct invariant holds (enqueue→commit→unlink — *audit confirms this ordering is sound*); Redis-outage behavior decays to floor; **a part is never committed `Replicated` unless every declared chunk is present and verified**; a transient mismatch never terminally discards a healthy part.

## Phase 2 — Observability & operability (can't run prod — or staging — blind)

**Goal:** make the drain's health visible and self-healing on fault. The plan scoped this to metrics; the audit adds the probe/exit-code items because, post-cutover, invisibility is an availability risk *now*.

**Work:**
- **[P1] R2 — drain OTLP metrics exporter + "S3 Drain" Grafana dashboard; instrument the un-instrumented Python loops (MPU reaper etc.).** The seam is already built (`snapshot.rs`); export path is OTLP gRPC push to `:4317` (verified). Start with a small high-signal set, grow later (each metric is one line once the exporter exists). *(plan; audit finding 15)*
  - Must include the currently-silent conditions: **breaker-open** (today logged at `debug`, same path as normal rate-limiting — `worker.rs:141-146`) and **stuck-defer** (a permanently-deferred part is indistinguishable `warn` spam and is deliberately kept out of `error_bps`).
  - "Coordinator health" on the gate = **leader-election convergence + epoch/fence sanity**, not just liveness.
- **[P1] ➕ Liveness probe + health signal on both binaries.** Neither the agent nor the allocator has a `livenessProbe` or an inbound health endpoint (`probe.rs` is an *outbound* ceph-mgr client). A *hung* (not crashed) pod — e.g. a broken redis `ConnectionManager`, cf. the 2026-06-19 crash-loop — stays `Running` and never restarts → silent permanent per-node upload outage (sole producer). Exec-liveness on heartbeat/lease freshness, or a small health server. *(audit finding 5; NEW — plan had only *readiness* in Phase 3; liveness is the more urgent one and belongs here)*
- **[P1/P2] ➕ Non-zero exit on worker fault.** `main.rs:93-95` returns `Ok(())` regardless of the `RunReport`; a panicked worker tears the agent down but exits 0 → no CrashLoopBackOff, no alert, looks like a clean SIGTERM. *(audit finding 7; DOC — R6, elevated)*

**Gate:** drain throughput, replication lag, backlog, failures, reclaimed, **coordinator/leader + epoch health**, and DLQ depths visible on the staging dashboard; a hung or panicked pod is restarted by k8s and surfaces an alert.

## Phase 3 — Drain hardening / DB & infra hygiene

**Goal:** bounded resource use and no rough edges at scale. The plan covered PG hygiene + resilience polish; the audit adds the coordination-Redis eviction fix (its single biggest omission) and three resilience items.

**Work:**
- **[P2] R3 — batch the reconciler `status()` query.** `reconcile.rs:158` does an O(N) per-part SELECT each cycle. *(plan)*
- **[P2] R4 — GC terminal `cephor_replication_status` rows.** No terminal DELETE exists; the table grows and the reconciler scans it. *(plan)*
- **[P2/P3] R5 — resilience polish:** defer-cap, AIMD EWMA + dead-band + safe floor, full-jitter backoff, **worker readiness probes**. *(plan)*
- **[P3] R6 — fence + lint + small-safety:** `write_allocations` lease revalidation, `arithmetic_side_effects`/`indexing_slicing` lints, `O_NOFOLLOW` on SSD opens (F5), supervisor semantics. *(plan)*
- **[P1] ➕ Coordination Redis eviction (interim mitigation).** `coordination.rs:52` + `k8s/redis-cluster/staging.yaml:28` — redis-queues is `allkeys-lru`; the `cephor:epoch` fence counter has **no TTL and is never read** → prime LRU eviction victim → eviction resets epoch to 1 → the legit leader is permanently fenced by cached higher-epoch alloc keys → allocator deadlock, fleet decays to floor, *worst under the memory pressure the drain exists to handle*. Interim: guarantee the epoch's persistence (seed/floor, or a separate handling) so a memory spike can't reset the fence. Permanent fix = **Phase 7** (dedicated Redis). *(audit finding 3; NEW — absent from the plan; note this is an infra/config issue distinct from R6's Lua lease-revalidation)*
- **[P2] ➕ `Probing` breaker deadline.** `enforce.rs:78-89` — `Probing` has no timeout; if the single half-open probe drain is cancelled/panics without recording an outcome, the breaker denies *all* drains on the node until restart. *(audit finding 8; NEW)*
- **[P2] ➕ Carve non-Ceph errors out of the Ceph breaker.** `worker.rs:168-172` — a Postgres blip on `mark_replicated` or a `PartClaimLost` maps to `CephFailure` and can open the node-global breaker despite a healthy Ceph (feedback loop under load). *(audit finding 9; NEW)*
- **[P2] ➕ Per-call Redis timeouts.** The `ConnectionManager` has no response timeout; a reachable-but-blocked redis-queues (fsync stall/BGSAVE/swap) parks the tick loop indefinitely — the error-retry path never fires on a *hang*. *(audit finding 13; NEW — pairs with the Phase 2 liveness probe)*
- **[P2] ➕ Allocator-before-agent deploy ordering.** `kustomization.yaml` — the allocator owns the `cephor_*` schema/migrations but the agent DaemonSet has no initContainer waiting on it → agents CrashLoop on a fresh namespace. Add an init-wait or documented apply order. *(audit finding 14; NEW — also relevant to Phase 6 runbooks)*
- **[P2] ➕ Source `HIPPIUS_UPLOAD_BACKENDS` from the secret.** `drain-agent-daemonset.yaml:99-100` hardcodes `"arion"` while Python workers read the shared secret → adding a backup backend silently under-replicates (the drain never enqueues it, so the janitor replication gate never clears → unbounded cache growth). *(audit finding 11; DOC — PR-199 P3; also a Phase 6 durability item)*

**Gate:** bounded PG churn (batched reconciler, terminal rows pruned); no unbounded backlog or cache growth; the coordination fence survives Redis memory pressure; the breaker can't wedge and doesn't trip on non-Ceph faults.

## Phase 4 — Scale validation (staging + chaos)

**Goal:** prove throughput/lag under load and that every failure self-recovers with no data loss. The plan's design is strong; the audit sharpens the chaos matrix and the "no data loss" gate.

**Prerequisite (moved up from later):**
- **[P1] ➕ Add Redis to the `rust` CI job.** `test-and-lint.yml:232-247` wires postgres but no Redis and never sets `CEPHOR_TEST_REDIS_URL` → ~12 coordination tests (fencing, election, lease/heartbeat expiry, budget apply/decay) **skip silently and pass green.** Fix this *before* chaos — don't spend expensive chaos runs rediscovering coordination bugs a Redis-enabled CI catches for free. Stopgap: convert the silent skips to `#[ignore]` so the gap is visible. *(audit finding 4; NEW)*

**Work:**
- 1 GB MPU benchmark + replication-lag experiment. *(plan)*
- Burst/spike test: SSD fill vs reclaim vs pressure-503s. *(plan)*
- Chaos: kill a drain node, Redis blip, Ceph degradation. *(plan)* — **sharpen:**
  - Redis: include **memory-pressure/eviction** (exercises finding 3) and **hang** (exercises finding 13), not just a blip/restart.
  - Ceph: include a case that produces **non-Ceph** errors (PG blip mid-commit) to confirm the breaker doesn't trip (finding 9), and a cancelled/paniced probe drain to confirm no `Probing` wedge (finding 8).
  - **Data-integrity fault injection:** drop/corrupt an interior chunk on SSD and confirm the part is *not* committed `Replicated` and the SSD copy is retained (exercises findings 1/2/10).
- **➕ End-to-end object checksums** after every chaos run, so "no data loss" is *verified*, not assumed.

**Gate:** measured throughput acceptable; replication lag bounded; every failure self-recovers; **byte-for-byte object integrity confirmed by checksum** after node kill / Redis eviction+hang / Ceph degradation.

## Phase 7 — FINAL: prod network topology decision meeting

**Goal:** settle the hardware/isolation/scaling shape (can't be inferred from code) and produce a signed-off topology + cutover runbook.

**Agenda (plan) + audit additions:**
- SSD ingest nodes — which/how many, SSD sizing vs replication-lag + pressure thresholds. *(relates to finding 15 — SSD fill is the failure mode when the drain stalls.)*
- Taints / isolation — taint PG-NVMe nodes off ingest; label/taint dedicated SSD nodes; nodeAffinity allow-list for api-local + drain-agent. *(matches scale-hardening Tier 0.1.)*
- Scaling strategy — drain-agent DaemonSet + allocator singleton placement, api-local replica count, ingest-vs-read scaling, graceful node add/drain.
- ATS fleet + cutover — nodes/region, cache sizing, config ownership, AuthProxy-vs-token, staged cutover order + rollback triggers.
- **➕ Dedicated `noeviction` Redis (or separate instance) for drain coordination**, isolated from the LRU work-queue Redis. This is the permanent fix for finding 3 and it is a topology decision, not a code change — you cannot fix it with a per-key TTL under `allkeys-lru`. *(audit finding 3)*

**Gate:** signed-off topology + cutover runbook; coordination-Redis isolation decided.
