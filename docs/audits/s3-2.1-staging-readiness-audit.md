## Executive summary

The Rust drain-core is well-engineered (a sealed `PartVerified` marker makes
"commit before verify" a compile error; `claim_seq` fencing tokens; saturating
arithmetic with no reachable overflow/unwrap panics found), and the API-side upload
enqueue is correctly gated behind `HIPPIUS_DRAIN_GATED_UPLOAD_ENABLED`. **However,
the branch is not production-ready as-is** — there are two regressions on the
*current* default path, several silent data-never-uploaded / duplicate-upload paths
that block flipping the drain-gated flag, and a handful of live drain durability
gaps.

### What is actually live (critical framing)

- **`HIPPIUS_DRAIN_GATED_UPLOAD_ENABLED=false`** in staging and prod today. Most
  drain-gated-upload findings are **latent until the flag is flipped** — *except*
  **F1** and **F2**, which affect the ungated default path right now.
- **The Rust `drain-agent` DaemonSet is running and replicating in staging now.** It
  replicates SSD→CephFS and unlinks the SSD source after marking a part replicated.
  So the drain durability findings (**F8–F10**) are **live**, not gated. (Note: the
  GC/eviction subsystem `gc_object`/`claim_gc` is *not* yet wired into the agent
  runtime; the normal drain unlink path *is*.)

### Remediation priority

| When | Findings |
|---|---|
| **Before next prod deploy** (flag stays off) | F1, F2 — regress the live default upload path |
| **Before flipping the drain-gated flag** | F3, F4, F5, F6, F7 — silent data-never-uploaded / duplicate uploads / silent stalls |
| **Harden while drain runs in staging** | F8, F9, F10 — low-probability but silent data-loss / liveness; cheap guards |
| **Before scale** | P1, P2 — performance, worsen unbounded over time |

## Tier 1 — affects production today (flag OFF)

### F1 · Uploader's `all_parts_on_pool` deferral is ungated 🔴 CONFIRMED

**Location:** `workers/run_arion_uploader_in_loop.py:62` (flag read but unused;
`config.py:85`).

**Description.** The new "are all parts on ceph yet?" check and its defer-to-retry-ZSET
behavior run on *every* dequeued upload, unconditionally. It is **not** guarded by
`HIPPIUS_DRAIN_GATED_UPLOAD_ENABLED`, so it executes on the default production path
where the API still enqueues at PUT time.

**Impact.** On `main`, a transient meta-visibility lag (cross-pod CephFS propagation,
a retry dequeued during a brief read miss) was absorbed by an inline
`get_meta_with_wait` (~30s) inside `process_upload`. Now `all_parts_on_pool` returns
`False` with no wait and the request is bounced through the retry ZSET on a 5s cycle
(`uploader_not_ready_delay_seconds`). A genuinely-stuck/orphaned upload that
previously DLQ'd in ~30s can now churn the ZSET for up to
`uploader_not_ready_max_wait_seconds` (1800s) before DLQ. This is a behavior change
to the ungated path that ships to prod regardless of the flag.

**Recommendation.** Gate the entire `all_parts_on_pool`/defer block behind
`config.drain_gated_upload_enabled`. With the flag off, the uploader should behave
exactly as on `main` (straight to `process_upload`). Add a test asserting the
flag-off path does not call `all_parts_on_pool`.

### F2 · Past `max_wait`, "routing to DLQ" has no `return` — falls through 🟠 CONFIRMED

**Location:** `workers/run_arion_uploader_in_loop.py:73-77`.

**Description.** When `all_parts_on_pool` is `False` and `waited >=
uploader_not_ready_max_wait_seconds`, the code logs `"… routing to DLQ"` but has no
`return`/`continue`. The only `return` is in the sibling `waited < max_wait` branch
(line 72). Execution falls straight into `process_upload` at line ~93.

**Impact.** `process_upload` runs against parts known to be absent from ceph,
re-paying the per-chunk `get_meta_with_wait` and **holding an inflight slot** for the
full meta-wait window before raising — reintroducing exactly the head-of-line
blocking the defer logic was added to avoid. The log line is also misleading: nothing
routes to the DLQ here; it only happens later if/when `process_upload` raises and the
attempt count is exhausted.

**Recommendation.** `continue` (or explicitly push to the DLQ) immediately after the
warning instead of falling through. Correct the log message to reflect what actually
happens.

## Tier 2 — must fix before flipping the drain-gated flag

### F3 · Sweep never filters `address IS NOT NULL` → parts loop forever, never upload 🔴 CONFIRMED (mechanism)

**Location:** `hippius_s3/sql/queries/promoter_sweep_unpromoted.sql:14`;
`hippius_s3/workers/upload_promoter.py:42`; emit at
`crates/hippius-drain-core/src/store.rs:705`.

**Description.** The drain emits `cephor_replicated` for *every* part it replicates,
unconditionally. The sweep selects any replicated part lacking a `chunk_backend` row,
with no `object_versions.address` predicate. `promote_part` returns `False` when
`address IS NULL` and never creates a `chunk_backend` row.

**Impact.** Any replicated part that reaches the sweep with a NULL `address` (legacy
rows, rows written before the flag flip, any non-promoter write path) is re-selected
on every sweep (default 30s) **forever**, and is **never uploaded to a backend** — a
silent durability gap (the object is "complete" to the client but absent from Arion),
plus perpetual sweep busy-work.

**Recommendation.** Add an `EXISTS`/join predicate so the sweep only returns parts
whose `object_versions.address IS NOT NULL`. Separately, decide the policy for
genuinely address-less replicated rows (alert + DLQ rather than silent infinite
retry).

### F4 · NOTIFY + sweep double-enqueue; DLQ wall-clock ceiling never trips 🟠 CONFIRMED

**Location:** `hippius_s3/workers/upload_promoter.py:126,140` (both `put_nowait` to a
plain `asyncio.Queue`); re-stamp at `hippius_s3/queue.py:134`.

**Description.** Nothing dedups in-flight promotions. A part promoted via the NOTIFY
callback but not yet committed to `chunk_backend` (upload still in flight) is
re-found by the next sweep and enqueued again with a fresh `request_id`. Separately,
each re-promote builds a *fresh* `UploadChainRequest`, and `enqueue_upload_to_backends`
stamps `first_enqueued_at` only when `None` — so a re-promoted part resets its
wall-clock clock every cycle.

**Impact.** (a) **Duplicate Arion upload** for any part whose promotion→upload spans
a sweep boundary — the uploader's `ON CONFLICT` insert dedups the resulting DB row
but *not* the redundant Arion POST / chain publish / billing. (b) A permanently-stuck
part is re-promoted every 30s, so its wall-clock ceiling never accumulates and it
**never reaches the DLQ** — it ping-pongs forever with no fault surfaced.

**Recommendation.** Add an in-flight dedup (a `SET NX EX` promotion lock per
`(object_id, version, part)`, mirroring the existing download-coalesce lock) so the
NOTIFY and sweep paths cannot both enqueue. Preserve `first_enqueued_at` across
re-promotes (carry it on the part/row, not the transient request) so the DLQ ceiling
still bounds a stuck part.

### F5 · LISTEN has no reconnect + sweeper DB calls have no timeout → silent total stall 🔴 CONFIRMED

**Location:** `hippius_s3/workers/upload_promoter.py:118` (bare `asyncpg.connect`,
no `add_termination_listener`), `:137` (`db_pool.acquire()`/`fetch()` with no
timeout; pool `max_size=10`, no `command_timeout`).

**Description.** The dedicated LISTEN connection has no termination listener,
reconnect loop, or health check. A Postgres restart / failover / TCP blip silently
kills the subscription; the pod stays "healthy" parked on `work_q.get()` and all
future NOTIFYs are lost. The sweeper — the sole backstop — has no timeout on its DB
calls, so a hung/exhausted pool blocks both the sweeper and the main work loop
indefinitely.

**Impact.** Promotion silently degrades to sweep-only (loss of low-latency promotion),
and in the combined failure (dead listener + hung pool) **all promotion stops with no
crash and no k8s restart** — uploads stall invisibly.

**Recommendation.** Register `add_termination_listener` and reconnect-with-backoff on
the LISTEN connection (re-issue `add_listener` on reconnect); add a liveness signal
that fails if neither a NOTIFY nor a successful sweep has occurred within N intervals.
Add `command_timeout` to the pool and/or `timeout=` on the sweep/`promote_part` DB
calls so a hung pool can't wedge the loop.

### F6 · Sweep ignores `cb.deleted` → soft-deleted-only parts look "uploaded" forever 🟠 CONFIRMED

**Location:** `hippius_s3/sql/queries/promoter_sweep_unpromoted.sql:14` (compare
`hippius_s3/sql/queries/count_chunk_backends.sql:24`, which uses `WHERE NOT
cb.deleted`).

**Description.** The anti-join keys on `cb.chunk_id IS NULL`, but a soft-deleted
`chunk_backend` row (`deleted = true`) still has a non-NULL `chunk_id`, so the part is
treated as already-promoted and excluded from the backstop.

**Impact.** A part whose only backend rows were unpinned/soft-deleted is never
re-uploaded — it has no *live* backend copy, yet the janitor's
never-evict-until-replicated gate keeps its SSD copy pinned indefinitely (cache
pressure that never resolves).

**Recommendation.** Add `AND NOT cb.deleted` to the join/filter so only live backend
rows count as "promoted," matching `count_chunk_backends.sql`.

### F7 · Flipping the flag silently changes MPU upload identity (subaccount → main_account) 🟠 CONFIRMED

**Location:** `hippius_s3/api/s3/multipart.py:1048` (gated: `main_account`) vs `:1059`
(non-gated: `account.id`).

**Description.** The gated MPU-complete persists `address =
request.state.account.main_account`; the non-gated branch enqueues `address =
request.state.account.id` (the requesting subaccount). The `address` field drives
chain-publish identity, backend account attribution, metrics
(`hippius.account.main`), and the DLQ/dedup key — not crypto.

**Impact.** Flipping the flag changes the upload identity for the same MPU operation.
Notably, `main_account` is the **correct** value — the simple-PUT path already uses
it, so the non-gated MPU `account.id` is a pre-existing anomaly the flag actually
*fixes* — but the change is silent and alters chain/metrics/DLQ attribution at
cutover.

**Recommendation.** Align the non-gated MPU branch to `main_account` now (decoupled
from the flag) so identity has one source of truth, or delete the non-gated branch
when the gate lands. Document the attribution change in the cutover runbook.

## Tier 3 — Rust drain durability (live in staging; low reachability, cheap fixes)

### F8 · Empty (meta-only) part dir commits `Replicated` with zero data, deletes SSD source 🟠 CONFIRMED

**Location:** `crates/hippius-drain-core/src/partdrain.rs:260-295`; reachable empty
list at `crates/hippius-drain-agent/src/localfs.rs:228-247`.

**Description.** There is no `chunks.is_empty()` or `meta.num_chunks` cross-check. If
`list_chunks` returns empty (part dir + `meta.json` present, but no `chunk_*.bin`),
the per-chunk verify loop never runs, `persist_meta` + `mark_replicated` commit the
part as `Replicated`, and `remove_part` deletes the SSD source. The sealed
`PartVerified` proof attests "the loop ran," not "the loop ran ≥ once."

**Impact.** A part is marked durably replicated with zero chunk data on the pool and
the source gone — silent data loss / zero-length object on read. Only reachable if the
API's meta-last write invariant is ever violated (API bug, partial cleanup that
removed chunks but left meta), but the drain trusts that invariant with no defense.

**Recommendation.** Cheapest guard in this set: before commit, assert `!chunks.is_empty()`
and (ideally) cross-check against `meta.num_chunks`; on mismatch mark the part failed
rather than replicated.

### F9 · Idempotent fast-path unlinks SSD on the DB marker alone 🟠 CONFIRMED

**Location:** `crates/hippius-drain-core/src/partdrain.rs:249-255`.

**Description.** When a part's status is already `Replicated`, `drain_part` unlinks
the SSD source and returns without confirming the CephFS pool copy still exists
(no `ceph.chunk_hash`/existence probe).

**Impact.** If the pool copy was lost out-of-band after the original commit (CephFS
data loss, an operator `rm`, a future GC bug), a re-drive of the same part deletes the
only surviving copy — the SSD source. The window is narrow (commit → crash before
unlink → pool copy independently lost → re-drive) but there is zero defense-in-depth.

**Recommendation.** Add a pool-existence/hash probe before the fast-path unlink; if
the pool copy is missing, re-drive (re-copy) rather than unlink.

### F10 · NULL-`claimed_at` draining row wedges forever; parent-dir fsync omitted; meta not byte-verified 🟡 CONFIRMED

**Location:** `crates/hippius-drain-core/src/store.rs:610` (re-claim selector),
`reconcile.rs:173` (tallied `in_flight`, not re-recorded); `localfs.rs:206`
(`sync_parent_dir` fsyncs only the leaf); `partdrain.rs:285` (meta persisted without
verify).

**Description.** Three related, lower-probability gaps:
- A node-stamped `draining` row with NULL `claimed_at` (legacy / interrupted older
  agent) is invisible to the lease re-claim (`NULL < now() - lease` is never true),
  is counted `in_flight` by the reconciler, and is not cleaned by migration 0006
  (node is set) or 0007 (no backfill) — that part **never drains**. (The
  NULL-`claim_seq` variant is *not* a wedge — `claim_part` overwrites it on re-claim
  and the fencing guard handles NULL safely.)
- `persist_into` fsyncs the file and the leaf `part_<n>` dir but not the intermediate
  `<object>/` and `v<version>/` directory entries that `create_dir_all` may have just
  created — a crash after `mark_replicated` can orphan the subtree (reduced, but not
  provably zero, on CephFS).
- `meta.json` is committed without the byte-level hash verification every data chunk
  receives — an inconsistent asymmetry (small blast radius: a tiny fsync'd,
  atomically-renamed file, more likely to fail a JSON parse than serve wrong data).

**Impact.** Liveness (a permanently un-drained part pinning its SSD copy) and a narrow
crash-durability window; the meta asymmetry is mostly a robustness/consistency nit.

**Recommendation.** (a) Backfill/clean node-stamped `draining` rows with NULL
`claimed_at` (one-shot migration) or special-case them in the re-claim selector. (b)
fsync the intermediate parent dirs in `persist_into` (or fsync up to the cache root).
(c) Optionally hash-verify `meta.json` for symmetry with chunks.

## Performance (not blockers; worsen over time)

### P1 · Unindexed `replicated`-status sweep seqscans an unbounded table every 30s 🟠 CONFIRMED

**Location:** `promoter_sweep_unpromoted.sql:6` (`WHERE crs.status = 'replicated'`);
indexes in `crates/hippius-drain-core/migrations/0005_*.sql` (only partial indexes for
`status='pending'`/`'draining'`); terminal rows retained per `0006_*.sql:19-21`.

**Description.** `replicated` (terminal) rows are kept forever and no index covers
`status='replicated'`. Every sweep (default 30s) sequentially scans all replicated
rows ever — and because the un-promoted set is normally empty, it full-scans to
return zero rows — then joins `parts → part_chunks → chunk_backend`. This runs against
the same ceph-backed Postgres the whole S3 2.1 effort is meant to relieve.

**Impact.** A steady-state background scan whose cost grows monotonically with total
parts ever drained. Bounded (2 scans/min, off the user-facing path) but unbounded in
growth.

**Recommendation.** Add a partial index matching a "needs-promotion" predicate, or GC
fully-promoted terminal rows, or introduce a distinct status
(`replicated_unpromoted` → `promoted`) that an index can target.

### P2 · Allocator writes allocations every tick even when unchanged 🟡 CONFIRMED

**Location:** `crates/hippius-drain-core/src/tick.rs:78` (`write_allocations`
unconditional; only an empty-plan correctness guard exists).

**Description.** `run_tick` rewrites all per-node allocations on every leader tick
(default 5s after `dfe29b4`), each an `INSERT … ON CONFLICT DO UPDATE` hot-row write —
a slow WAL fsync (measured 2–5s on the ceph-backed Postgres) — even when the AIMD plan
is identical to the prior epoch.

**Impact.** Continuous steady-state fsync churn on the contended Postgres on a quiet
cluster.

**Recommendation.** Short-circuit `write_allocations` when the plan equals the
last-written set — but still periodically refresh `updated_at`, since agents treat
un-refreshed allocation rows as stale and decay toward their floor
(`store.rs:356-359`). The leader-lease renewal write is separate and remains.

## Cleared — do not chase

- **`upload_id`-by-newest-row mismatch is cosmetic, not data corruption.** The
  promoter derives `upload_id` via `SELECT … ORDER BY initiated_at DESC LIMIT 1` keyed
  on `object_id` only (`upload_promoter.py:37`), so an overwritten object can get a
  stale `upload_id`. **But** `upload_id` is **not** in the AEAD AAD (the active
  `AESGCMChunkedAdapterV2` ignores it; envelope AAD is `bucket:object:version`) and
  **not** in the backend path (uploader uses `part_chunks.id` for the filename + the
  Arion-returned hash); the derived `resolved_upload_id` is dead after
  `uploader.py:316`. No undecryptable-chunk risk. **Action item:** the
  `writer/CLAUDE.md` "crypto binding" note claiming the AEAD binds `upload_id` is
  **stale/wrong** and should be corrected.
- **The copy-verify "TOCTOU" is not exploitable.** Parts are write-once,
  content-addressed, meta-gated, and single-writer-claimed (`FOR UPDATE SKIP LOCKED`
  + `claim_seq`), so no concurrent source rewrite can occur. (Refuted.)
- **The redis BRPOP-timeout-fatal regression was NOT reintroduced.** The defer path
  reuses the `with_redis_retry`-wrapped uploader queue ops. Minor inconsistency: the
  promoter's own `enqueue_upload_to_backends` is not wrapped in `with_redis_retry`
  (unlike the uploader) — worth aligning for resilience parity.
- **Flag-off promoter parking forever** (`upload_promoter.py:104`,
  `await asyncio.Event().wait()`) is real but adequately mitigated by the documented
  "flip the flag on BOTH the promoter and api-local, then redeploy" cutover procedure.
  There is no in-code enforcement of the ordering — it relies on the runbook.
