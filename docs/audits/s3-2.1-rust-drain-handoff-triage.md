## TL;DR (the easy version)

The Rust drain (the service that copies uploaded object parts off the ingest SSD onto CephFS) is
running on staging and doing its job — but **it is invisible.** It reports nothing to Grafana, so we
can't see whether it's keeping up, failing, or silently wedged. That's the one thing we need to fix
before release.

Two of the six proposed PRs matter *now*; the other four are good hygiene we can do after the release
flip.

- **R1 — small safety fix (½ day).** During a Redis outage the drain keeps draining at its last
  budget forever instead of backing off. This is the exact failure the drain is supposed to protect
  against. Tiny fix.
- **R2 — wire metrics into Grafana (2–3 days). THE RELEASE BLOCKER.** All the numbers already exist in
  the code; they just aren't exported. We add the exporter plumbing once, pick a small number of
  signals, and add two lines of Kubernetes config. Then the drain shows up on the existing staging
  dashboard automatically — no dashboard changes needed.
- **R3–R6 — defer.** Query batching, row cleanup, resilience tuning, and lint hygiene. All real, none
  release-gating.

**Recommendation:** do R1 + R2 now (independent, can run in parallel). Ship everything else after the
release flag flips.

**On metric scope:** start with **4–5 signals total**, not the ~17 the handoff lists (those are
placeholders). The expensive part of R2 is the exporter wiring, which is one-time; each metric after
that is a single line, so we can grow the set later for free.

## R1 — decay-on-`Err` in the allocation pull  [P1, ~½ day]

**The problem.** Each cycle the agent pulls its byte budget from Redis. Today:

- `Ok(Some(budget))` → apply the new budget.
- `Ok(None)` (budget key TTL-expired) → **decay** toward the floor.
- `Err(...)` → **just log and keep the current budget** ← the bug.

On a *sustained* redis-queues outage the pull keeps erroring, so the agent holds its last budget
indefinitely and keeps draining at full rate into a possibly-degraded Ceph — misbehaving in exactly
the incident the drain exists for.

**Verified:** `crates/hippius-drain-agent/src/runtime.rs:280` — the `Err` arm logs and returns without
touching the rate; the `Ok(None)` arm at `:279` already calls `decay_rate(...)`.

**Fix.** In the `Err` arm, apply the same `decay_rate(base, floor, now - allocated_at, half_life)` the
`Ok(None)` arm uses. The enforcer floor (`enforce.rs` `decay_rate`, clamps to `[floor, base]`, never 0)
guarantees it can neither starve nor overrun.

**Test.** A `run_alloc` unit test that returns `Err` for N polls and asserts the rate decays toward the
floor (today's decay test only covers `Ok(None)`).

## R2 — OTLP metrics exporter (Grafana parity) — THE RELEASE BLOCKER  [P1, ~2–3 days]

### Why this is the one that matters

The drain-agent DaemonSet is live and replicating on staging, but every signal it produces
(`AgentSnapshot`, circuit-breaker state, allocator fleet estimate, fenced ticks) is **tracing-only** —
invisible to Grafana. We cannot answer "is the drain keeping up / failing / wedged" from a dashboard.
Python workers already flow to Grafana; the drain must match before we rely on it in prod.

### The good news: the seam is already built

`snapshot.rs` was explicitly designed for this (its own doc comment references "the observability layer,
M9, feature `otel`"). **Every value is already computed — there is nothing new to measure, only to
export:**

- `AgentSnapshot` already exposes `drained`, `failed`, `deferred`, `reconciler_recovered`, `reclaimed`,
  plus `p99()` and `error_bps()`.
- `heartbeat_once()` (`runtime.rs:178`) already reads snapshot p99 / error_bps / disk usage every tick —
  the natural place to record.
- `ConcurrencyLimiter::in_flight()` (`enforce.rs:227`), `BreakerState` (`enforce.rs:26`), and the
  allocator's `plan.controller.total()` fleet estimate (`run.rs:41`) all exist and are read today.

### Export path (confirmed against the live cluster + Python)

```
Rust drain (OTLP gRPC push, 10s)  ─►  otel-collector  ─►  prometheus-server (monitoring ns)  ─►  Grafana
   OTEL_EXPORTER_OTLP_ENDPOINT          :4317 receive       scrapes collector :8889              monitoring.hippicode.com
   = http://otel-collector:4317         :8889 prom-export   job "otel-collector-staging"          /d/hippius-s3-system-load
```

- Python uses OTLP **gRPC push** to `:4317` via `PeriodicExportingMetricReader` (`hippius_s3/otel_setup.py:43-63`).
  **No HTTP `/metrics` server is needed** — same model for Rust.
- The collector's Prometheus exporter has `resource_to_telemetry_conversion: enabled`, so OTLP resource
  attributes become Prometheus labels (`service_namespace`, `service_name`, `service_instance_id`,
  `deployment_environment`).
- The staging dashboard's `var-namespace` filter keys on **`service_namespace`** — so
  `service.namespace=hippius-s3-staging` is what makes the drain panels appear.
- **Proof a headless push worker already works end-to-end:** the janitor's `fs_store_parts_on_disk`
  reports under `service_namespace=hippius-s3-staging` today. The drain uses the identical push model.

### Confirmed gap

Both drain manifests — `k8s/staging/drain-agent-daemonset.yaml` and `drain-allocator-deployment.yaml` —
have **zero OTEL env**, so nothing is emitted even in principle. `drain_*` = 0 series in Prometheus. The
template to mirror lives in `k8s/base/workers-deployments.yaml` and `k8s/staging/environment-patch.yaml`.

### Recommended metric set — start small (4–5 signals)

> The handoff lists ~17 metrics; those are placeholders. **The cost of R2 is the exporter plumbing,
> which is one-time. Each metric after that is a single `.observe()` line.** So starting small shrinks
> review surface and dashboard clutter — not real effort — and the set grows trivially later.

One "is it working" signal + one "is it silently broken" signal per side:

**Agent (drain):**
| Metric | Type | Reads | Answers |
|--------|------|-------|---------|
| `drain_parts_replicated_total` | counter | `AgentSnapshot::drained` | Is it working / throughput? |
| `drain_ssd_backlog_bytes` | gauge | `usage.used_bytes` (already in `heartbeat_once`) | Is it keeping up? (backlog growth → SSD fills → every PUT on the node 503s — the most operationally important gauge) |
| `drain_breaker_open` *(optional 3rd)* | gauge 0/1 | `BreakerState` | Is Ceph silently refusing us? (the breaker trips silently today) |

**Allocator:**
| Metric | Type | Reads | Answers |
|--------|------|-------|---------|
| `drain_leader` | gauge 0/1 | leadership result | Did leader election converge? (the #1 allocator health question) |
| `drain_fleet_estimate_bps` | gauge | `plan.controller.total()` | What budget is being handed to the fleet? |

Naming convention (matches the handoff): `drain_*`, counters end `_total`, gauges unsuffixed.

### Implementation outline (one PR off `staging`)

1. Add `opentelemetry` + `opentelemetry-otlp` (+ SDK, tonic/gRPC) to the workspace, behind an `otel`
   cargo feature on the agent + allocator crates.
2. Init a `MeterProvider` with a periodic OTLP exporter in each binary's `main` (`agent/main.rs`,
   `allocator/main.rs`); set `service.name` in code or via `OTEL_SERVICE_NAME`.
3. Register the gauge callbacks that read the already-computed snapshot / breaker / allocator state —
   hook into the existing periodic loops (`heartbeat_once`, the allocator tick).
4. Add the OTEL resource-attr env to the two manifests (mirror the janitor deployment exactly):
   ```yaml
   - name: OTEL_RESOURCE_ATTRIBUTES
     value: "deployment.environment=$(ENVIRONMENT),service.namespace=$(K8S_NAMESPACE),service.instance.id=$(POD_NAME)"
   - name: OTEL_SERVICE_NAME          # agent: hippius-drain-agent   allocator: hippius-drain-allocator
     value: "hippius-drain-agent"
   ```
   (`K8S_NAMESPACE` / `POD_NAME` / `ENVIRONMENT` already come from the downward-API env on the pods.)
5. Tests: unit-test the snapshot→instrument mapping; a smoke test that the `MeterProvider` builds.

**Build gate before push** (strict workspace lints — `-D warnings`, `unwrap_used=deny`, `panic=deny`):

## R3–R6 — defer to after the flag flip

- **R3 — batch reconciler `status()`.** Verified O(N) per-part loop at `reconcile.rs:158` (the reconciler
  is the sole drain trigger). Add a batched `Store::statuses(&[PartKey])` using one `IN (UNNEST(...))`
  query, chunked ~500/query. Matters at backlog scale; not release-gating.
- **R4 — terminal-row GC for `cephor_replication_status`.** No terminal DELETE exists; `replicated`/`failed`
  rows accumulate and the reconciler scans the table. Add a periodic batched sweep with a
  `CEPHOR_STATUS_RETENTION_SECS` knob. Slow burn.
- **R5 — resilience polish (4 splittable sub-items).** Defer cap on re-defers; AIMD EWMA + dead-band +
  safe floor; full-jitter backoff; **worker readiness probes**. Pull the readiness probe forward if you
  want clean rollouts (k8s currently considers a not-yet-leading pod ready).
- **R6 — fence + lint + small-safety.** `write_allocations` lease revalidation; enable
  `arithmetic_side_effects` + `indexing_slicing` lints and fix the ~39 verified-safe sites; `O_NOFOLLOW`
  on SSD chunk opens; **supervisor exit-non-zero** so k8s restarts a pod whose worker died (pairs with
  R5's readiness probe).
