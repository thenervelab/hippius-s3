# S3 2.1 — Rust drain production-readiness review

**Date:** 2026-07-01
**Branch:** `staging`
**Method:** 6 parallel deep-review agents (core data-safety, control plane, agent runtime, allocator+probe, k8s+Python integration, tests/CI), every serious finding then verified by hand against source.
**Supersedes framing in:** `s3-2.1-staging-readiness-audit.md` (2026-06-22), `s3-2.1-scale-hardening-proposals.md` (2026-06-25). Code has moved since (PR #212 Redis coordination, #214 janitor reclaim, the breaker/ENOENT fix).

---

## TL;DR (the easy version)

**The good news:** the drain's core data path is well-built. The scariest failure — "delete the SSD copy before the CephFS copy is safe" — does **not** happen on the normal or common-failure paths: the drain copies → fsyncs → verifies → enqueues → commits → *then* unlinks, and several previously-flagged bugs (zombie double-commit, breaker-tripping-on-benign-errors) are genuinely fixed. The allocator math, token bucket, lease/claim logic, and the producer→consumer wire contract are all sound and (mostly) well-tested.

**The one thing everyone must understand first:** this is **not gated behind a flag anymore.** The old `HIPPIUS_DRAIN_GATED_UPLOAD_ENABLED` switch is gone — it was a hard cutover. On staging *right now*, the API no longer enqueues uploads at PUT; **the Rust drain is the sole upload producer, with no fallback.** If the drain stalls on a node, that node's uploads stop. Every "availability" finding below is therefore *live*, not latent.

**What must be fixed before we trust this in production** (details + evidence below):

1. **Data integrity — the drain deletes the SSD source without checking the part is complete.** It trusts the directory listing, byte-verifies only the first and last chunk, and never validates against `meta.json`'s declared chunk count. A missing or torn *interior* chunk can be committed as "Replicated" and the only good copy deleted. **[P1, data-loss class]**
2. **The coordination brain lives on a Redis that is allowed to throw its keys away.** redis-queues runs `allkeys-lru`; the split-brain fence counter has no TTL and is never read, making it the first thing evicted under memory pressure — which deadlocks the allocator exactly during the incidents the drain exists to handle. **[P1]**
3. **CI is green but runs zero coordination tests.** No Redis in the CI job → all ~12 fencing/election/lease tests skip silently. The riskiest layer is the least verified. **[P1]**
4. **No liveness probes and no health endpoint on either drain binary.** A *hung* (not crashed) pod = a silent, permanent per-node upload outage that Kubernetes never restarts. **[P1, elevated by the no-fallback cutover]**
5. **A faulted worker exits 0.** A panicked worker tears the agent down but reports success, so there's no CrashLoopBackOff and no alert — it looks like a clean shutdown. **[P1/P2]**

Plus a cluster of P2s (breaker can wedge in `Probing`; non-Ceph errors trip the Ceph breaker; `mark_failed` can discard a healthy part; `HIPPIUS_UPLOAD_BACKENDS` hardcoded → silent under-replication; ancestor-dir fsync gap) and several P3 polish items.

**Bottom line:** the machine is well-engineered but is currently flying **blind** (no metrics, no probes, no restart-on-fault) and **untested where it's riskiest** (coordination), while being **on the critical path with no fallback**. None of the P1s are deep rewrites — they're a completeness check, a Redis policy/knob, a CI service, two probes, and an exit code. That's a realistic pre-prod punch list, not a redesign.

## Critical context: the hard cutover (verified)

- `HIPPIUS_DRAIN_GATED_UPLOAD_ENABLED` exists **only in old audit docs** — not in any `.py`, `.rs`, or `.yaml` (verified by grep).
- `hippius_s3/api/s3/objects/put_object_endpoint.py:198-211` and `multipart.py:1072-1081`: the API **unconditionally** stops enqueuing at PUT and only persists the object address; the drain reads it and produces the upload after replication.
- Consequence: the drain is a hard dependency of the write path on staging today. Prior audits' "most bugs are latent until the flag flips" no longer applies. **All availability findings are live.**
- Prod note: there are **no production drain manifests yet** (staging-only). At prod cutover the drain must ship *before/with* the api image that stops PUT-enqueue, or prod uploads stall.

## Findings by severity

Legend: **NEW** = not in a prior audit · **DOC** = already documented (still open) · **FIXED** = previously flagged, now resolved.

### P1 — Data integrity

**1. The drain deletes the SSD source without a completeness check against `meta.json`. [NEW]**
`crates/hippius-drain-core/src/partdrain.rs:338-388`. The drain copies whatever `chunk_<i>.bin` files `list_chunks` returns, byte-verifies only the first and last (`:347`), persists `meta.json` (`:366`), commits `Replicated` (`:385`), then unlinks the SSD source (`:387`). It reads `meta.json` only to *copy* it — it never parses `num_chunks`/`size_bytes` to confirm the part is whole.
*Failure:* a part whose `meta.json` is present (so the scan admits it) but an interior `chunk_<k>.bin` is missing or zero-length (corruption, partial cleanup, an interrupted overwrite that dropped a chunk after meta landed) is copied as a *reduced* set; both sampled endpoints pass; it commits `Replicated` and the SSD source — the only complete copy — is deleted. Permanent, silent truncation. RADOS checksums cannot detect a *missing* chunk.
*Mitigating factor:* the api writer writes `meta.json` last, so on the happy path "meta present ⇒ all chunks present." The exposure is post-meta corruption/partial-state, not steady state. But the delete is irreversible and the check is cheap, so this is defense-in-depth on the one operation that can't be undone. *Fix:* parse `meta.json`, assert the copied chunk set matches `num_chunks` (and no zero-length chunk) before commit/unlink.

**2. Interior chunks are committed unverified, on a rationale that is factually wrong. [NEW]**
`partdrain.rs:330-362` (see the comment at `:334-337`; there's even a test named `a_corrupt_interior_chunk_is_not_caught_by_the_sampled_readback` at `:812`). Only first/last are re-read from CephFS and compared to the copy-time hash. The justification — *"content-addressed naming makes writes idempotent… interior chunks trust the copy"* — is wrong for the part model: chunks are **path-addressed** (`chunk_<index>.bin`), not content-addressed, and once `Replicated` there is **no re-drive** (`claim_part` never re-selects a replicated row — see finding 13). So a torn interior pool write (page-cache/kernel/mount fault before RADOS checksums it; a short write reported as success) is committed and the SSD deleted, with no later correction.
*Context:* the sampling was introduced by PR #212 ("hash-once + sampled readback"); the 2026-06-18 audit credited a *full* per-chunk readback. This is a deliberate throughput trade, but the stated safety rationale doesn't hold. *Fix:* either restore full readback, or re-justify sampling honestly against RADOS end-to-end checksums and document the residual window.

### P1 — Coordination / availability

**3. Coordination state lives on an `allkeys-lru` Redis that can evict it; the epoch fence has no TTL. [NEW — found independently by 2 agents, verified]**
`crates/hippius-drain-core/src/coordination.rs:52` (`INCR` on `cephor:epoch`, **no `EXPIRE`**) + `k8s/redis-cluster/staging.yaml:28` / `production.yaml:23` (`maxmemory-policy allkeys-lru`). The module's whole premise is "these keys are TTL-keyed — expiry is the death signal," but `allkeys-lru` evicts by recency **regardless of TTL**, and redis-queues also carries the real upload/download work queues + pub/sub, so memory pressure is realistic — and most likely during the exact backlog/incident the drain targets.
The epoch counter is the worst case: it's `INCR`'d only on takeover and never read, i.e. the least-recently-used coordination key, and it has no TTL so even `volatile-lru` semantics wouldn't have spared it under `allkeys-lru`.
*Failure:* leader A holds epoch 50 with live `cephor:alloc:*` keys stamped 50; the counter is LRU-evicted; a takeover `INCR`s the now-missing key → returns **1**; the new leader's `write_allocations(epoch=1)` is rejected by `WRITE_ALLOC_SCRIPT` (`:83`, sees stored `epoch 50 > 1`) → the *legitimate* leader is **permanently fenced** until every alloc key TTL-expires, while the whole fleet decays to floor. Epoch reset also destroys the monotonicity the entire F4 fence depends on. AOF does not help — eviction drops keys from the AOF too.
*Fix:* move coordination to a `noeviction` instance/logical DB, or seed/guard the epoch with a persisted floor. This is the single highest-leverage infra fix. (The fence *logic* is otherwise sound — this eviction hole is the one way a stale/reset epoch lands budgets.)

**4. CI is green but runs zero coordination tests. [NEW — verified]**
`.github/workflows/test-and-lint.yml:232-247`: the `rust` job wires a `postgres:17` service but **no Redis** and never sets `CEPHOR_TEST_REDIS_URL`. Every Redis-gated test hits its `else { eprintln!("skipping…"); return; }` and **passes without executing** — ~12 tests: `coordination.rs` (4), `tick.rs` (3), `runtime.rs` (3), `run.rs` (2).
*Consequently unverified on every PR:* epoch fencing / split-brain prevention, leader election + lease expiry/renewal, heartbeat fleet aging, allocation apply + runtime decay. A regression here stays green. This is the same layer as finding 3 — riskiest and least tested.
*Fix:* add a Redis service + `CEPHOR_TEST_REDIS_URL` to the job. As a stopgap, convert the silent skips to `#[ignore]` (shows as "ignored", not "passed") so the gap is at least visible. Note the runtime decay/apply tests have 5s busy-wait windows flagged as starvation-prone — expect timing flakes when Redis is first wired.

**5. No liveness probes and no health endpoint on either drain binary. [P1 — NEW; elevated by the no-fallback cutover]**
`k8s/staging/drain-agent-daemonset.yaml` and `drain-allocator-deployment.yaml` define no `livenessProbe`; neither binary starts an inbound HTTP server (`agent/main.rs`, `allocator/main.rs` — `probe.rs` is an *outbound* ceph-mgr client). If the tokio runtime *wedges* rather than crashes (a persistently-broken redis `ConnectionManager` — cf. the 2026-06-19 redis-queues crash-loop incident — or a poisoned lock), the pod stays `Running` and never restarts.
*Failure (agent):* that node's uploads silently halt forever — and since the drain is the sole producer, that's a per-node upload outage with no self-recovery. *Failure (allocator):* a hung leader stops writing budgets, agents decay to floor fleet-wide, no restart. `replicas:1 + Recreate` on the allocator is correct; the gap is purely the missing liveness check.
*Fix:* exec-liveness on heartbeat/lease freshness (or add a small health server). Pairs with handoff R5.

**6. `run_alloc` `Err` arm holds the last budget forever instead of decaying. [DOC — handoff R1, confirmed by 3 agents]**
`crates/hippius-drain-agent/src/runtime.rs:280`. `Ok(None)` decays (`:279`); `Err(...)` only logs. Sustained redis-queues outage → agent keeps draining at last budget into a possibly-degraded Ceph. *Fix:* apply the same `decay_rate(...)` in the `Err` arm. Small, and now also the untested arm (finding 4).

**7. A faulted worker exits 0; no per-worker restart. [DOC — F10/F21/handoff R6, elevated]**
`hippius-drain-agent/src/main.rs:93-95` returns `Ok(())` regardless of the `RunReport`; `supervisor.rs:195-207` escalates any single worker exit (incl. panic) to a full shutdown. So a worker panic tears the agent down *and* reports success — the container exits 0, reads as a clean SIGTERM, produces no CrashLoopBackOff and no alert. DaemonSet `restartPolicy: Always` does restart it, but the fault is invisible. No test asserts the exit-code mapping. *Fix:* exit non-zero on `WorkerExited`/`!clean`. (Whether to add bounded per-worker restart vs keep fail-fast is a design call — but the exit code is a must.)

### P2 — Correctness & resilience

**8. The circuit breaker can wedge permanently in `Probing`. [NEW — verified]**
`enforce.rs:78-89` — `Probing` has no deadline (unlike `Open { until }`), and only `record_outcome` leaves it. `worker.rs`'s RAII `release_permit` (on a cancelled/panicked `drain_part().await`) deliberately leaves the breaker untouched. If the single half-open probe drain unwinds without recording an outcome, the breaker is stuck in `Probing` and `allows()` denies **all** future drains on the node until process restart. Narrow trigger, silent permanent node-wide stall. *Fix:* a `Probing` deadline, or have the recovery path reopen the breaker.

**9. Non-Ceph errors are classified as Ceph failures and can open the node-global breaker. [NEW]**
`worker.rs:168-172` — `is_benign_deferral` covers only `Enqueue` and ENOENT `Io`. A `mark_replicated` failure (a Postgres blip *after* the Ceph copy succeeded) or a `PartClaimLost` from lease-expiry re-claim maps to `CephFailure`, trips the breaker after 5, and halts all draining on the node despite a healthy Ceph. Mild feedback shape under load (slow drains → lease expiry → PartClaimLost → breaker → more backlog). *Fix:* carve out `Store`/`PartClaimLost` from the Ceph error domain.

**10. `mark_failed` is unguarded and a `ChunkMismatch` discards the pool copy with no retry. [NEW]**
`store.rs:581-597` (no `status`/`claim_seq` guard, unlike the fixed `mark_replicated`) + `partdrain.rs:349-360` (marks failed, then `ceph.remove_part`, no copy-retry; `ssd_reclaim` later deletes the failed SSD source after grace). *Failure A:* a *spurious/transient* readback mismatch terminally discards a healthy part — pool copy removed, SSD reclaimed after grace = both tiers gone. *Failure B:* a stale zombie claimant hitting a mismatch flips a part another agent is actively draining to `failed` (the live commit then correctly fails `PartClaimLost`, so no double-unlink, but the row is wrongly `failed`). *Fix:* `claim_seq + status='draining'` guard on `mark_failed`, and a bounded copy-retry before terminal-failing.

**11. `HIPPIUS_UPLOAD_BACKENDS` is a hardcoded literal on the drain → silent under-replication. [DOC — PR-199 P3, still open]**
`drain-agent-daemonset.yaml:99-100` hardcodes `"arion"`, while every Python worker reads it from the `hippius-s3-secrets` key. The agent is the sole producer and this list picks the `{backend}_upload_requests` queues it fans out to. Add a backup backend to the secret and the drain keeps enqueuing to `arion` only → parts never enqueued to the new backend → the janitor replication gate (`UPLOAD_BACKENDS ∪ BACKUP_BACKENDS`) is never satisfied → **SSD/CephFS never evicted (unbounded cache growth) + objects silently absent from the second backend.** Latent while the set is `[arion]`. *Fix:* source from the same secret; log the resolved list loudly at startup.

**12. Ancestor directory entries are never fsync'd. [NEW — regression vs the 2026-06-18 audit]**
`localfs.rs:269-283` (`copy_into` does `create_dir_all`) + `:434-438` (`finalize_part` fsyncs only the part dir). The part dir's dentry in the version dir, and the version dir's dentry in the object dir, are never fsync'd. *Failure:* crash right after `mark_replicated` commits but before ancestor-dentry writeback → on reboot the pool part dir is unreachable while the row says `Replicated`; `claim_part` won't re-select it, the reconciler counts it `replicated_orphan` and leaves it, `ssd_reclaim` skips replicated — nothing rebuilds it → stranded/unreadable object (a leak, not deletion). Practical risk is lower on real CephFS (MDS-journaled namespace ops), but `LocalFs` is written generically. *Fix:* fsync ancestor dirs on first create, or document the CephFS-only durability assumption.

**13. Allocator can hang (not just error) with no recovery. [NEW — partial overlap with 5]**
`coordination.rs` — the `ConnectionManager` has no per-call response timeout; `run_allocator` catches *errors* and retries but a *hung* await never returns. A reachable-but-blocked redis-queues (fsync stall, BGSAVE, swap) parks the tick loop indefinitely, the lease isn't renewed, all alloc keys TTL-expire, the fleet decays to floor, and (finding 5) no probe restarts the pod. *Fix:* per-call timeouts + the liveness probe.

**14. No allocator-before-agent ordering gate. [NEW]**
`k8s/staging/kustomization.yaml` — the allocator owns `cephor_*` schema/migrations on startup, but the agent DaemonSet has no initContainer waiting for it (contrast mpu-reaper, which waits on `postgres-rw`+`redis-queues`). `kubectl apply -k` on a fresh namespace → agents CrashLoop for the migration window (and transitional migration `0009` drops tables an old agent build might still read). Self-heals, but racy/noisy and contradicts the manifest's "allocator-first" claim. *Fix:* initContainer waiting on a schema marker, or documented apply ordering.

**15. Observability blind spots that are dangerous with no fallback. [NEW/DOC]**
Independent of the known "no metrics at all" (handoff R2), three conditions are invisible even to log scraping today:
- An **open breaker halting a node** is logged at `debug` on the same path as ordinary rate-limiting (`worker.rs:141-146`); the SSD then fills silently until PUTs 503. *Elevate to `warn` + a `drain_breaker_open` metric.*
- A **permanently-stuck deferred part** (e.g. `address` never finalized) re-defers forever, logged as identical `warn` spam, and is deliberately kept out of `error_bps` — a genuinely wedged object looks exactly like transient backpressure. *Add a defer-count/age signal.*
- A **faulted worker exits 0** (finding 7) — looks clean.

### P3 — Polish / hardening

- **AIMD estimate balloons during ceph-mgr probe blindness** (`alloc.rs:303`): the controller keeps additively ramping toward `max_total` while blind, so on probe recovery `capacity = min(max_total, ceiling)` snaps to full rate — a thundering burst into a just-recovered cluster. Consider forcing back-off (or freezing the estimate) while blind. [NEW]
- **Blind probe can never reach `Critical`** (`probe.rs:133`): on mgr-down-then-Ceph-fills, the fleet drains at the decayed floor into a full cluster rather than buffering. Backstopped by Ceph blocking writes → agent `error_bps` feedback, so fail-*degraded* not fail-open. Worth an alert on `consecutive_failures`. [NEW]
- **No `securityContext`; pods run as root** (both manifests). The agent needs root for cross-uid unlink on the shared RW hostPath, but the allocator (no mounts) could run non-root; add cap-drops/`seccompProfile`. [NEW]
- **`Recreate` + slow image pull can exceed the 15s allocation TTL** → fleet throttles to floor on every allocator deploy. Document or shorten startup. [NEW]
- **The `AlreadyReplicated` crash-recovery fast path is structurally unreachable** via the normal trigger (`partdrain.rs:322-328` vs `claim_part` never selecting `replicated`) → the SSD orphan from a commit→unlink crash is never reclaimed (the known residual leak, now explained: the recovery path only runs in unit tests). [NEW framing]
- **Symlink-following file opens (no `O_NOFOLLOW`)** in `localfs.rs` `hash_file`/`stream_copy_hash` (F5, still open): a symlink planted in the shared SSD tree could make the drain copy an arbitrary file into the pool. [DOC]
- **Heartbeat/skipped-replicated/allocator-tick failures are all log-only** — slow fleet-wide starvation from a recurring `warn` with no metric. [mostly DOC — R2]

## What's solid — confirmed FIXED or SAFE (do not re-chase)

The review deliberately tried to break these and could not:

- **The delete-before-durable data-loss path is closed on the normal/common-failure paths.** Ordering is copy → fdatasync each chunk → sample-verify → persist meta last → one dir-fsync → **enqueue → commit → unlink** (`partdrain.rs:373-387`). Enqueue precedes commit and unlink, so "data enqueued nowhere" is impossible; every error variant retains the SSD copy; `PartVerified` makes commit-before-verify a compile error. (Findings 1/2/12 are the residual edges, not the mainline.)
- **F4 zombie double-commit is FIXED** — `claim_seq` fencing now guards `mark_replicated` (`store.rs:562-577`, tested).
- **F18 FIXED** — `mark_failed` clears `claimed_at`.
- **PR-199 P1 FIXED** — enqueue/`NotReady`/vanished-source (ENOENT) errors are benign deferrals (`BreakerSignal::Deferred`), not Ceph-breaker trips (`worker.rs:157-196`, well-tested).
- **The producer→consumer wire contract is byte-verified both directions** via a shared golden fixture (`tests/fixtures/upload_chain_request.golden.json` ↔ `enqueue.rs` test ↔ `tests/unit/test_upload_chain_request_wire.py`); consumer confirmed at `workers/run_arion_uploader_in_loop.py:125`.
- **Allocator math is sound** — no over-allocation (`capacity = new_total.min(ceiling.budget())`), no div-by-zero (empty-fleet/zero-weight guarded), `u128` intermediates throughout, conservation proptested on feasible and infeasible paths.
- **Token bucket + `decay_rate` math is sound** — exact integer refill with remainder carry, saturating/clamped, never below floor, never above base; proptested.
- **The split-brain fence logic is sound** (two-pass atomic Lua; a deposed leader surfaces `Fenced`) — *except* the LRU-eviction hole (finding 3).
- **No fail-open ceiling** — every probe failure decays toward the floor; it never reads a blind probe as unlimited (wiremock-tested, runs in CI).
- **Claim/lease correctness is sound** — a `draining` row always has a non-NULL `claimed_at`; claims are node-scoped; stale claims reclaim after the lease. No NULL-`claimed_at` wedge.
- **`ssd_reclaim` is fail-safe** — only aged `failed` parts; pending/draining/replicated/no-row never touched.
- **Config validation fails fast and completely** in both binaries; no missing-env crash-loop (the Python "full-config-set" trap does not apply — the Rust binaries have their own minimal required sets, all present in the manifests).
- **Workspace lints are real and enforced in CI** — `unwrap_used=deny`, `panic=deny`; `clippy -D warnings` + `cargo deny` run. No unguarded `unwrap`/`expect` in non-test code found.
- **Path/node/volume invariants line up** between the api-local cache, the drain hostPath, and the ingest node affinity lists.

## Suggested pre-production punch list

Ordered by leverage. None are rewrites.

**Must-fix before prod (P1):**
1. Completeness check against `meta.json` before commit/unlink (finding 1) + decide the interior-chunk verification policy (finding 2).
2. Move drain coordination off `allkeys-lru` — dedicated `noeviction` instance/DB, or a persisted epoch floor (finding 3).
3. Add Redis to the `rust` CI job so coordination tests actually run (finding 4).
4. Liveness probes / health signal on both binaries (finding 5) + non-zero exit on worker fault (finding 7).
5. Decay-on-`Err` in the allocation pull (finding 6 / handoff R1).

**Strongly recommended (P2):**
6. `Probing` breaker deadline (8); carve non-Ceph errors out of the Ceph breaker (9); guard + retry `mark_failed` (10); source `HIPPIUS_UPLOAD_BACKENDS` from the secret (11); per-call Redis timeouts (13); allocator-before-agent ordering gate (14); elevate the breaker-open + stuck-defer signals (15).
7. Wire the metrics exporter (handoff R2) — it's the umbrella that makes 5/7/13/15 observable.

**Nice-to-have (P3):** the polish list above.

**Prod-cutover checklist:** ship the drain (allocator → agents) *before/with* the api image that stops PUT-enqueue; add prod drain manifests with `REDIS_QUEUES_URL` + secret-sourced `HIPPIUS_UPLOAD_BACKENDS`; include the allocator/agent/reaper in the prod kustomization.
