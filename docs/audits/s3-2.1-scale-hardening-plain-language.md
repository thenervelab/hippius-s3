# S3 2.1 Scale Hardening — Plain-Language Breakdown

A non-specialist explainer of the production-scale recommendations. No infra/k8s background needed.
For the technical version (with file:line evidence and citations), see
[`s3-2.1-scale-hardening-proposals.md`](s3-2.1-scale-hardening-proposals.md).

**As of:** 2026-06-25, after the drain-direct (PR #199) and MPU-abort (PR #200) merges.

---

## The setup, in everyday terms

Think of our storage system as a **busy shipping depot**:

- A customer drops a package at a **drop-off desk** (a fast local disk on one specific machine). We
  hand them a receipt instantly — "got it."
- A **courier** then carries that package from the desk to the **main warehouse** (our shared storage,
  "Ceph"), and also ships a copy to a **permanent off-site vault** (our durable backend, "Arion"). The
  vault is the copy that really counts — the desk and warehouse are just fast working space.
- A **ledger book** (the database, "Postgres") records where every package is.
- A **dispatcher** decides how fast each courier is allowed to move, and a **safety switch** stops
  couriers if the warehouse gets jammed.

The recent code merge fixed several problems already. Here's what's fixed, what to do next, and why.

---

## Already fixed (good news) ✅

- **The safety switch used to trip for the wrong reason.** It was wired so that "the paperwork isn't
  ready yet" looked the same as "the warehouse is broken," so it would needlessly shut down a courier
  — and because that courier is now the *only* one doing shipping, it could freeze all shipping on
  that machine. Now the system tells those two situations apart.
- **Reading a just-uploaded file used to send people on a pointless errand.** If you uploaded a file
  and immediately tried to read it, the system would sometimes go knock on the off-site vault's door
  for a copy that wasn't there yet, wait, fail, retry — instead of just looking in the warehouse where
  the courier had already put it. Now it checks the warehouse first.
- **Abandoned uploads used to pile up forever.** If a customer started a big multi-part upload and
  walked away, the leftover pieces sat around indefinitely. There's now a cleanup worker that sweeps
  those away after a while. Mostly fixed (it tidies the ledger; some leftover packages on the desk
  still need the disk-cleanup work below).

---

## Do first — the courier is too slow ⬅️ top priority

This is now the most important thing, because after the merge **that one courier is the only one
doing all the shipping.** If they fall behind, *everything* backs up.

- **Stop stamping every single box separately.** Right now, for each piece of a file, the courier
  carefully logs it to permanent disk and waits for confirmation — one piece at a time. That waiting
  is the single biggest slowdown. We can log a whole batch at once at the end instead. This is the
  kind of change that can make the courier many times faster.
- **Stop double-checking work we don't need to double-check.** For every piece, the courier currently
  re-reads *both* the original and the copy from scratch to make sure they match — doubling the disk
  work. Because of how the files are named, we already have a cheaper way to guarantee they match, so
  we can drop the expensive re-read.
- **Let more than four boxes move at once.** The courier is capped at handling four things at a time,
  and that cap is fixed no matter how idle or busy things are. Make it adjustable so it can speed up
  when there's a backlog.

**Net effect:** uploads land in the permanent vault much faster, and backlogs clear quickly instead
of dragging.

---

## Do next — make it sturdy under load 🛡️

- **The database is on the worst possible disk.** Our ledger book lives on the *same* shared storage
  the couriers are hammering. So when the couriers get busy, writing to the ledger crawls (we've
  measured multi-second delays for a single entry). The fix: **give the ledger its own fast, dedicated
  disk** so the couriers and the bookkeeping stop fighting each other. This one change quietly
  de-risks a lot.
- **Don't let scratch notes clog the main ledger.** Heartbeats ("I'm still alive"), speed-limits, and
  other constantly-changing scratch data are being written into the durable ledger, which is heavy and
  slow. That kind of throwaway info belongs in a lightweight fast notepad (Redis) we already run.
  Bonus: it also removes a nasty circular dependency where, if the warehouse is struggling, the very
  system meant to *fix* the warehouse can't write down what it's doing.
- **The drop-off desk has no cleanup crew.** The warehouse gets tidied automatically, but the small
  fast drop-off desk does not. If the courier falls behind, that desk fills up — and once it's full,
  **we start turning away new customers on that machine even though the warehouse has plenty of room.**
  It also lives on the machine's main disk, so a full desk can knock the whole machine sideways. We
  need a cleanup routine for the desk, plus alerts before it fills.
- **Stop retry pile-ups from becoming a stampede.** When something fails, workers retry — but with no
  overall budget and no randomized spacing, a brief hiccup can spiral into everyone retrying at once
  and keeping the system down even after the original problem is gone. The industry-standard fix is a
  retry "allowance" plus randomized timing. (We've actually been bitten by exactly this kind of
  pile-up before.)
- **Stop the health-checker from shooting healthy machines.** Our "is this machine alive?" check is
  too twitchy: when a machine is simply *busy*, the check times out and the system **restarts it** —
  making the overload worse, in a loop. The fix is to make a busy machine quietly *stop taking new
  work* (and recover) rather than get killed. (This also matches a real incident we had.)
- **Two slow-but-real bookkeeping issues:** the dispatcher rewrites its speed-limit notes every few
  seconds even when nothing changed, and one tracking table grows forever with no cleanup. Both add
  steady, pointless load. Small fixes, just need doing.

---

## The infrastructure track (for whoever runs the data center) 🏗️

These are physical/setup changes rather than code:

- **One filing clerk is becoming a bottleneck.** All the lookups ("where is this file?") go through a
  single clerk, and our files-are-many-and-small pattern overwhelms one clerk. The fix is to run
  several clerks and split the work between them. Standard, well-understood.
- **Watch the fullest shelf, not the average.** The warehouse can refuse writes when *any single
  shelf* gets full, even if it looks only ~85% full overall. We should rebalance shelves and alert on
  the fullest one, not the average — and shield normal traffic when the warehouse is repairing itself
  after a hardware failure.

---

## The big strategic decision 🎯

- **Right now, a package only exists in one place for a short window before it's safely copied.** We
  tell the customer "got it" the instant the package hits *one* drop-off desk — before it's been
  copied anywhere else. If that one machine dies in that window, those just-received packages are
  stuck until the hardware comes back. This is essentially the same single-point-of-failure problem
  this whole project was meant to kill — we've spread it across a few machines instead of eliminating
  it.
- **The industry-standard answer** (what Google, Meta, and the big systems do) is to **copy the
  package to a second machine before saying "got it."** It costs a tiny bit of upload latency in
  exchange for never losing the window. **This is a genuine trade-off decision for the team to make**
  — it's the real fix for "a machine died and took recent uploads with it."

---

## Future — the planned "front desk" cache (ATS) 🛎️

We've designed, but not built, a **front desk that keeps copies of popular files** so readers don't
walk to the warehouse every time. When we build it, three things matter most:

- **Don't accidentally hand a private file to the wrong person.** The front desk would hold *unlocked*
  copies, so the rules about who's allowed to see what have to be airtight. The safe default is: only
  cache files that are *meant* to be public, and double-lock anything private.
- **Don't let a popular file cause a stampede.** If a thousand people ask for the same not-yet-cached
  file at once, the front desk should fetch it *once* and share, not send a thousand runners to the
  warehouse.
- **Handle big files and partial downloads gracefully** — fetch in chunks rather than re-grabbing the
  whole thing.

---

## The one-paragraph version

The recent merge already fixed the scariest reliability bugs. The biggest remaining win is simply
**making the courier faster** (it's now the only one shipping, and it's slowed down by over-cautious,
one-at-a-time habits). After that: **give the bookkeeping its own disk**, **add a cleanup crew to the
drop-off desk**, and **move throwaway data off the heavy ledger**. The one real *decision* to make —
not just a fix — is whether to **copy each upload to a second machine before confirming it**, which is
what would finally eliminate the "a machine died and took recent uploads" risk for good.
