## 1. Executive summary

The implementation is **correctness-hardened but sits at the weakest point of three well-studied
spectra**, each with a textbook fix:

1. **Durability** — the gateway acks after a *single-node* write (≈ Kafka `acks=1` / HDFS
   `replication.min=1`). The node6 SPOF is **spread across ingest nodes, not eliminated**.
2. **Drain throughput** — per-file `fsync` + a double-readback hash + a fixed concurrency of 4 cap a
   node at **~50–150 MB/s, fsync-bound**, far below NVMe ingest speed → SSD backlog grows under load.
3. **Coordination** — a control plane (drain/allocator) stores its own state on
   **Postgres-on-Ceph**, the very data plane it coordinates. This is the mechanical cause of the
   measured **2–5 s WAL fsync** and a circular recovery dependency.

The highest-leverage work is **infra/shared-fate (Tier 0)** plus a handful of **cheap drain code
fixes (Tier 1)**. A full roadmap with sequencing is in §8.

## 2. The systemic root cause (read this first)

The entire S3 2.0/2.1 effort exists to **relieve the Ceph-backed Postgres** and **kill the node6
SPOF**. At scale, the current implementation partially works *against* both:

- **Postgres-on-Ceph + the drain's small-file storm = the 2–5 s WAL fsync.** Every PG commit fsync is
  a synchronous all-replica RADOS round-trip; sync-committed IOPS on Ceph RBD can collapse to
  ~20–30/s. If the drain's CephFS pools share OSDs with the Postgres RBD pool, every WAL fsync queues
  behind the drain's create+fsync storm.
  **mClock and RBD QoS will NOT fix this** — the drain is *client* I/O (not background recovery, so
  mClock's `high_client_ops` doesn't separate it), and RBD QoS only fences RBD *images*, not a CephFS
  writer. Only **physical OSD/pool separation** does.
  [Ceph CRUSH device classes](https://ceph.io/en/news/blog/2017/new-luminous-crush-device-classes/) ·
  [mClock config](https://docs.ceph.com/en/reef/rados/configuration/mclock-config-ref/)
- **The SPOF is spread, not eliminated.** SSD ingest is a `hostPath` (RWO-on-node, not movable);
  api-local + drain-agent are hard-pinned via `nodeSelector`. If an ingest node dies, every object
  whose parts are still on its SSD and not yet drained to CephFS is **unavailable until that hardware
  returns**. With ~2.5 min drain lag for a 1 GB object, that is "all writes to that node in the last
  replication window." It is node6 reproduced per-ingest-node.

## 3. Tier 0 — Infra & shared-fate (highest leverage, mostly ops)

### 0.1 — Physically separate Postgres from the CephFS drain pools 🔴
- **Problem:** the 2–5 s WAL fsync is the drain storm queuing in front of PG commit fsync on shared OSDs.
- **Fix:** a dedicated **NVMe device-class CRUSH rule** for the Postgres RBD pool, on OSDs separate
  from the CephFS data + metadata pools. Put the CephFS **metadata pool on NVMe** too (biggest
  single small-file win).
- **Why (industry):** mClock/RBD-QoS provably can't isolate a CephFS client writer from RBD; physical
  separation is Ceph's own recommendation for latency-sensitive pools.
  [Ceph hardware recs](https://docs.ceph.com/en/reef/start/hardware-recommendations/) ·
  [device classes](https://ceph.io/en/news/blog/2017/new-luminous-crush-device-classes/)
- **Effort:** Ops/Ceph. **Payoff:** de-risks everything PG-bound at once.

### 0.2 — Break the circular recovery dependency: move ephemeral coordination off Postgres-on-Ceph 🔴
- **Problem:** the drain/allocator store heartbeats, budgets, claims, and NOTIFY wakeups on
  Postgres-on-Ceph — the data plane they coordinate. When Ceph degrades (the scenario the drain
  *exists* for), WAL fsync spikes, the coordinator's writes stall, and it can't coordinate recovery
  of the thing it depends on.
- **Fix:** move **heartbeats + budgets/allocations + presence to Redis with TTL** (`SET … EX <ttl>`;
  expiry *is* the death signal — no reaper). They are loss-tolerant and have **no business reason to
  be durable**. You already run six Redis instances.
- **Why (industry):** AWS Well-Architected **REL11-BP04** ("rely on the data plane, not the control
  plane, during recovery") + **static stability**; Brandur on keeping ephemeral high-write state out
  of the primary.
  [REL11-BP04](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_withstand_component_failures_avoid_control_plane.html) ·
  [static stability](https://aws.amazon.com/builders-library/static-stability-using-availability-zones/) ·
  [Brandur ephemeral DB](https://brandur.org/fragments/ephemeral-db)
- **Effort:** Medium (Rust + schema). **Payoff:** removes a large fraction of PG write churn + breaks
  the circular dependency for liveness signaling.

### 0.3 — Multi-active MDS + ephemeral directory pinning 🟠
- **Problem:** a single active MDS is single-threaded/CPU-bound — **~1–2k creates/sec** once the
  working set exceeds cache. The drain's create+delete churn + the janitor's full-tree stat walk +
  per-GET stat fan-out (7 pod types mount the one CephFS) saturate it.
- **Fix:** `max_mds` → ~4 active ranks with **distributed-ephemeral pinning** keyed on `<object_id>`
  (the layout is naturally sharded); one **standby-replay** per rank; `mds_cache_memory_limit` ≥ 8 GiB;
  alert on `num_strays` (delete churn) and `MDS_CLIENT_RECALL` (reader cap-recall → MDS OOM risk).
- **Why (industry):** scales to a ~4-rank plateau; ephemeral pinning is designed for hot churning trees.
  [Ceph multimds](https://docs.ceph.com/en/reef/cephfs/multimds/) ·
  [subtree pinning](https://ceph.io/en/news/blog/2017/new-luminous-cephfs-subtree-pinning/) ·
  [cache config](https://docs.ceph.com/en/latest/cephfs/cache-configuration/)
- **Effort:** Ops/Ceph.

### 0.4 — Ceph near-full / rebalance guardrails 🟠
- **Problem:** pool free space is gated by the **single most-full OSD**, not the average — a
  write-heavy small-file workload fills unevenly, so writes start failing (`backfillfull` 0.90 halts
  self-heal; `full` 0.95 blocks **both** drain and Postgres) while the cluster looks ~85% full. A
  single OSD/host loss = peering stall + backfill storm in the writer's path.
- **Fix:** mgr balancer + `reweight-by-utilization`; mClock **`high_client_ops`** profile for recovery
  (this *does* apply — recovery is background); separate public/cluster networks; **alert on the
  most-full OSD, not the average**.
  [Ceph health checks](https://docs.ceph.com/en/reef/rados/operations/health-checks/) ·
  [troubleshooting OSD](https://docs.ceph.com/en/latest/rados/troubleshooting/troubleshooting-osd/)

## 4. Tier 1 — Drain throughput (cheap code, high ROI)

Per-node ceiling ≈ **50–150 MB/s, fsync-bound** (`partdrain.rs:261-280`, `localfs.rs:193-207`).

### 1.1 — Batch fsync; one dir-fsync per part; `fdatasync` not `fsync` 🔴
- **Evidence:** `persist_into` (`localfs.rs:193-207`) fsyncs the file **and** the part dir on **every
  chunk** — a 64-chunk part = 128 serialized fsyncs.
- **Fix:** copy all chunks, then **fsync the part directory once** before the meta rename; use
  `fdatasync` (skips atime/mtime). Batched fsync is ~100× faster than per-file.
- **Caveat:** `rename` fails across mount points (`EXDEV`) — stage the temp **on CephFS itself**,
  never write to NVMe and rename into Ceph. (Verify current temp placement.)
  [Percona fsync](https://www.percona.com/blog/fsync-performance-storage-devices/) ·
  [fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html) ·
  [rename(2) EXDEV](https://man7.org/linux/man-pages/man2/rename.2.html) ·
  [LWN durable-write recipe](https://lwn.net/Articles/457667/)

### 1.2 — Drop per-file fsync entirely if source-delete is gated on Arion durability 🔴 (highest ROI)
- **Rationale:** the industry rule (Alluxio `ASYNC_THROUGH`; "don't fsync if durable elsewhere") is
  valid only when another durable copy is **confirmed** — which is exactly your model: **Arion is the
  durability boundary; CephFS is a cache.** If the SSD source is unlinked only after Arion confirms,
  the CephFS write need not be fsync-durable.
  [Alluxio write types](https://www.alluxio.io/blog/4-different-ways-to-write-to-alluxio) ·
  [evanjones durability](https://www.evanjones.ca/durability-filesystem.html)

### 1.3 — Kill the double-readback hash; hash once during the copy stream 🔴
- **Evidence:** `drain_part` re-reads **both** the SSD source and the freshly-written CephFS copy
  end-to-end to SHA-256 every chunk (`partdrain.rs:266-267`, `localfs.rs:283/301`) — 2× read
  amplification on the slowest tier, purely to verify.
- **Fix:** compute the SHA **once while streaming the copy**; drop the Ceph readback (or sample it).
  Content-addressed chunk naming already makes writes idempotent + self-verifying (Git/restic/IPFS).
  [restic design](https://github.com/restic/restic/blob/master/doc/design.rst)

### 1.4 — Parallelize + make concurrency tunable 🟠
- **Evidence:** `DRAIN_CONCURRENCY=4` fixed (`runtime.rs:35`); the AIMD allocator tunes bytes/sec but
  **never concurrency**, so it can't hide fsync latency with more in-flight parts.
- **Fix:** configurable / p99-auto-scaled concurrency; consider multiple `noshare` CephFS mounts
  (single-stream ~200 MB/s → ~1 GB/s parallel).
  [croit benchmark](https://www.croit.io/blog/ceph-performance-benchmark-and-optimization)

## 5. Tier 2 — Resilience correctness (code)

### 2.1 — Error-domain separation on the Ceph breaker ✅ RESOLVED (PR-199)
- **Done:** `worker.rs` now classifies `PartDrainError::Enqueue` (the `NotReady`/`Redis` domain) as
  `BreakerSignal::Deferred` — it releases the concurrency permit but **neither trips the node-global
  Ceph breaker nor counts as `failed`**; only copy/verify/commit errors are Ceph failures.
  `defer_part` backs the part off, and a deferral does not abort the `drain_until_empty` burst.
- **Residual (optional hardening, lower urgency now):** the breaker still trips on a **consecutive
  count of 5** (`runtime.rs:31`), not a failure-*rate* over a minimum volume, and has no
  **slow-call-rate** trip for CephFS *brownout* (slow-but-200). Industry default is rate+min-volume
  (resilience4j 50%/100; Envoy 85%) + a slow-call trip + exponential open-duration backoff
  (Envoy 30 s→5 min). Worth doing eventually, but the wedge risk is gone.
  [resilience4j](https://resilience4j.readme.io/docs/circuitbreaker) ·
  [Envoy outlier detection](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/upstream/outlier)

### 2.2 — AIMD allocator: hysteresis + EWMA + safe-budget floor 🟠
- **Evidence:** the ceiling probe flaps Open↔NEARFULL per ~2 s tick → sawtooth budget; a dead/flapping
  allocator decays every node toward `CEPHOR_FLOOR_RATE_BPS` (~1 MB/s) (`runtime.rs:228-234`,
  `enforce.rs:239`).
- **Fix:** EWMA-smooth the control signal (RFC 6298 template, α=1/8); **separate trip-on/trip-off
  thresholds** (dead-band) on the `fs_cache_pressure` 85/95% bands; gentler decrease factor
  (β≈0.7–0.9 like CUBIC/Netflix, not TCP's 0.5); **floor the per-node budget at a value that still
  keeps up with median ingest**, and use **lease-based expiring budgets with a conservative safe
  capacity** on control-plane loss (Doorman); alert on no-leader.
  [Chiu & Jain AIMD](http://www.flux.utah.edu/~kwright/paper_summs/network_papers/chiu_jain.increase_decrease_analysis.html) ·
  [RFC 6298 EWMA](https://datatracker.ietf.org/doc/html/rfc6298) ·
  [Doorman design](https://github.com/youtube/doorman/blob/master/doc/design.md)

### 2.3 — Fix read-after-write: override `chunks_exist_batch` ✅ RESOLVED (PR-199, `37b228a`)
- **Done:** `DualFileSystemPartsStore.chunks_exist_batch` (`dual_fs_store.py:39-53`) now checks the
  primary (SSD) first, then re-checks the **fallback (ceph pool)** for the misses — so a part the
  drain has replicated to the pool (and unlinked from SSD) classifies `source="cache"` and no longer
  triggers a doomed Arion download enqueue. The "wait on the bell" path fires cleanly.

### 2.4 — SSD ingest tier: two-watermark write-back + eviction 🔴
- **Evidence:** `fs_cache_pressure` watches the SSD (`fs_pressure.py:19`) but there is **no eviction
  on the ingest tier** (README: "isn't size-enforced — no janitor on this tier yet"); the hostPath
  is on the **node root disk**. A stuck drain fills it → **every PUT on that node 503s even when the
  ceph pool is healthy**, and threatens the kubelet.
- **Fix:** the Linux page-cache model — a **background-drain watermark below the hard 503 watermark**,
  an **age-based flush**, keep the **never-evict-until-persisted gate** (CacheLib/Alluxio invariant —
  your janitor already enforces it for ceph), add a **write-around relief valve** (straight to CephFS
  when overwhelmed), and ship Ingest-tier eviction (delete oldest parts carrying a `replicated.json`
  marker). Alert on SSD free + drain lag.
  [kernel vm.rst](https://www.kernel.org/doc/html/latest/admin-guide/sysctl/vm.html) ·
  [CacheLib admission](https://cachelib.org/docs/Cache_Library_Architecture_Guide/navy_overview/)

### 2.5 — Retry budgets + full jitter (prevents the metastable crash-loops already seen) 🟠
- **Context:** the 2026-06-19 redis-queues backup crash-loop was a metastable-failure precursor
  (workers re-spinning on a transient BRPOP timeout).
- **Fix:** **token-bucket retry budget** (Google SRE: cap retries at 10% of requests; AWS SDK uses a
  14-token-per-retry bucket — fail fast when depleted) + **full-jitter backoff**
  (`random(0, min(cap, base·2^n))`); **jitter the `Retry-After`** so shed clients don't retry at
  `now+N` in lockstep. Chunk uploads are already idempotent (deterministic per
  object_id/version/part/chunk_index).
  [AWS backoff+jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) ·
  [metastable failures (HotOS'21)](https://sigops.org/s/conferences/hotos/2021/papers/hotos21-s11-bronson.pdf)

### 2.6 — Saturation fails *readiness*, not *liveness* 🟠 (death-spiral fix)
- **Context:** the 2026-06-14 liveness death-spiral — an aggressive probe killed busy-but-healthy pods.
- **Fix:** liveness endpoint must be **cheap and off the hot path** (no PG/Redis/Ceph/Arion);
  **asymmetric `failureThreshold`** (~3 readiness to shed fast, ~10 liveness to restart slowly);
  raise `timeoutSeconds`; add a startup probe. Saturation → readiness (shed), never liveness (restart).
  [k8s probes](https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/) ·
  [SRE cascading failures](https://sre.google/sre-book/addressing-cascading-failures/) ·
  [Jacobs: liveness probes are dangerous](https://srcco.de/posts/kubernetes-liveness-probes-are-dangerous.html)

## 6. Tier 3 — Postgres load relief (whatever stays on the primary)

Beyond moving ephemeral state to Redis (0.2). *(The per-commit `pg_notify` and the promoter sweep are
gone post-merge — see §0. These remain:)*

- **GC terminal rows / partition-and-drop** (pg_partman) — `cephor_replication_status` grows unbounded
  (terminal `replicated`/`failed` rows retained, migration `0006`). **Wire the GC worker** — still
  dead code (`gc_object`/`claim_gc` only in tests; not spawned in the agent runtime). This is also the
  only DB-side reclaim for abandoned-MPU rows the `mpu-reaper` doesn't cover.
- **Batch the reconciler's per-part `status()` SELECTs** into one `WHERE (…) IN (…)` query —
  `reconcile.rs:158` still issues a serial `status()` SELECT per discovered part every poll (O(N) in
  the SSD backlog), and it is now the **sole** drain trigger (no NOTIFY), so the poll can't be
  shortened without amplifying this.
- **Partial index on the active predicate** (`WHERE status IN ('pending','draining')`) so claim/scan
  paths never touch terminal rows on the unbounded table.
- **Aggressive per-table autovacuum** (`scale_factor=0.02, cost_limit=1000, cost_delay=0`) to survive
  SKIP-LOCKED dead-tuple bloat (others saw ~15× lock time); **bound long transactions** with a terminator.
- **`SET LOCAL synchronous_commit=off`** for non-critical writes — decouples them from the Ceph fsync.
- **HOT updates**: never index churning columns (`claimed_at`, `deferred_until`, heartbeat, budget);
  `fillfactor` 70–80.
- **Allocator: short-circuit unchanged allocation writes** — `tick.rs:81` still calls
  `write_allocations` unconditionally every leader tick (only an empty-plan noop guard exists); skip
  the write when the plan equals the prior epoch, but still refresh `updated_at` so agents don't decay
  to floor.
  [Brandur: PG queues](https://brandur.org/postgres-queues) ·
  [richyen: PG as a job queue](https://techcommunity.microsoft.com/blog/adforpostgresql/potential-consequences-of-using-postgres-as-a-job-queue/4514332) ·
  [Recall.ai: LISTEN/NOTIFY doesn't scale](https://www.recall.ai/blog/postgres-listen-notify-does-not-scale) ·
  [PG HOT updates](https://www.postgresql.org/docs/current/storage-hot.html) ·
  [PG async commit](https://www.postgresql.org/docs/current/wal-async-commit.html)

## 7. Tier 4 — The durability decision (architecture, for the team)

The gateway acks after a **single-node** write — ≈ Kafka `acks=1` / HDFS `replication.min=1`, the
weakest point of the spectrum, and why the SPOF is spread, not eliminated. Every strong system —
GFS, HDFS, Kafka `acks=all`, Ceph `min_size=2`, **Meta's Tectonic** (two chunk nodes, one cross-DC,
before ack) — acks only after ≥2 nodes hold the data, and solves the latency objection with
**pipelined/chain replication** (head→tail streaming), not by acking locally.

**Proposal:** replicate each part to a **second ingest node/AZ before returning 200**, pipelined to
preserve latency. This is the real fix for "node dies → its un-drained writes are unavailable."

**This is a genuine design decision** (added write latency vs. the single-SSD loss window) — flagged
as an explicit team call, not a cheap fix.
[GFS paper](https://pdos.csail.mit.edu/6.824/papers/gfs.pdf) ·
[Kafka replication](https://docs.confluent.io/kafka/design/replication.html) ·
[Tectonic (FAST'21)](https://www.usenix.org/conference/fast21/presentation/pan) ·
[HDFS architecture](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html)

## 8. Tier 5 — ATS edge tier (when built)

**Repo reality:** there is **no ATS server in the repo** — only the gateway-side contract
(Cache-Control middleware `gateway/middlewares/cache_control.py`, PURGE-on-write `ats_purge.py`,
auth-probe `auth_probe.py`, `buckets.is_cache_warm`) is merged to `main`; the `feat/cdn` deployment
is parked (`a02f05e` "Disabled deployment of cdn for now"). When the tier is built:

- **Auth-leak is the #1 risk** — the origin returns **decrypted plaintext** (KMS is server-side), so
  ATS caches plaintext bodies. Keep `proxy.config.http.cache.ignore_authentication=0` (never flip it),
  cache **public objects only** by default, and for the "private + warm" path add **`Vary:
  Authorization` + cachekey-by-principal** as defense-in-depth — don't rely solely on the authproxy
  firing on every hit.
- **Close the coalescing gap** (the explicitly-unsolved piece): read-while-writer +
  `open_read_retry_time ≈ origin latency` + the **`collapsed_forwarding`** plugin
  (`open_write_fail_action=1`), fronted by a **consistent-hash mid/shield tier** (`strategies.yaml`,
  `go_direct:false`) so a herd of misses collapses to ~1 origin fetch.
- **Range reads:** native ATS range handling is weak (full-object fetch on partial miss); use
  **`slice.so` + `cache_range_requests.so` at 1–4 MiB blocks** (aligns with 4 MiB chunking).
- **Footguns:** disk cache is a **ring buffer with no LRU** (use `cache_promote`); changing
  `storage.config` **wipes the cache**; cap `per_server.connection.max` to protect the
  decrypt-on-read origin.
  [ATS collapsed_forwarding](https://docs.trafficserver.apache.org/en/latest/admin-guide/plugins/collapsed_forwarding.en.html) ·
  [cachekey](https://docs.trafficserver.apache.org/admin-guide/plugins/cachekey.en.html) ·
  [slice](https://docs.trafficserver.apache.org/en/latest/admin-guide/plugins/slice.en.html) ·
  [strategies.yaml](https://docs.trafficserver.apache.org/en/latest/admin-guide/files/strategies.yaml.en.html)

## 10. Open decisions for the team

1. **≥2-node pre-ack vs single-SSD loss window** (Tier 4) — the core durability/latency tradeoff.
2. **Move coordination off Postgres-on-Ceph entirely** (Redis Streams / dedicated PG on local NVMe)
   vs. just relieving it (Tier 3) — REL11-BP04 argues for the former before scaling further.
3. **Ingest→CephFS replication-lag SLA + alert thresholds** (drain lag, SSD free %, breaker-open).
4. **Replay real chunk-access traces** (Loki/gateway audit) through the eviction policy before
   committing the ingest-tier watermark numbers — published cache numbers are web/CDN traces, untested
   on our 4 MiB-chunk range-read pattern.
